## Measurement boundaries

The production workload harness uses ten warmups per case, then sorts elapsed
samples and reports element `n/2` as median and `n*95/100` as p95 (zero-based).
Edit/history stages have 100 measured samples; cursor movement and explicit
document cloning have 500; editor-group rendering has 120; Find has 40.
These are within-process observations, not independent launch medians or
confidence intervals. The harness does not retain individual samples.

Editor-group rendering uses a 1920×1080 CPU pixel buffer, scale 1, embedded
JetBrains Mono, 14-pixel font, 20-pixel line height and 8.4-pixel character width.
Font/model construction and initial glyph-cache warmup are outside timing.
Completion and bracket matching are disabled in this harness; edit/history also
disables LSP. Returned effects are not executed, except for Find's explicitly
synthetic search/reply roundtrip. No native window is created.

Completion uses Divan 0.1.21 with its Rust allocation profiler and 100 requested
samples per case. Its allocation-instrumented timings are not interchangeable
with the production harness. Fixture creation is excluded where `with_inputs`
is used; retained-state probes reuse their initialized model/parser. Allocation
output distinguishes fresh allocations from growth and deallocation; it is not
whole-process RSS. Divan reports fastest/slowest/median/mean, not p95.

### Findings and next profiling targets

1. **Find cache misses and total search work:** the pending frame is small, but
   explicit actions requiring fresh matches can still pay a 6.8–7.2 ms synchronous
   scan at 100,000 lines. Profile that path and worker-result construction before
   interpreting the 0.37 ms pending frame as total response latency.
2. **Completion response allocation pressure:** conversion reaches 4.398 MB of
   fresh allocations per 1,000-item response. Trace ownership/materialization
   while preserving resolution and edit semantics; per-keystroke refiltering is
   a separate, cheaper path in this suite.
   The [September 8 follow-up](2026-09-08-completion-responses.md) addresses this
   finding with deferred serialization; the measurements here remain historical.
3. **Idle refresh and full width reflow:** near-duplicate recency refresh reaches
   4.692 ms at 32 snippets; full source rewrap reaches 3.389 ms at 10,000 lines.
   Profile these larger stages before tuning already-small blink/cycle updates.
4. **Forward multi-cursor edits:** two-pane edits cost substantially more than
   Undo/Redo here. Sample planning, Rope mutation and peer-pane state capture
   before further restructuring; the stage timings do not attribute that cost.
5. **Preserve bounded ordinary paths:** cursor movement is approximately flat
   across retained-history sizes, and short-line group rendering is similar
   between 10,000 and 100,000 lines. Keep these probes as regression checks.

| Recency                    | 8/32 open buffers with distinct 8 KiB snippets; idle fill, refresh, near-duplicate refresh, stable observation and request attachment                                           |

Edit/history assertions check text, stack sizes, cursor order/count/desired
columns, directional selections and active index after every stage. Fixture
resets are outside timing. These are unsaved scratch buffers: saved-content
comparison is not measured. Cursor/history's explicit Document clone is a
diagnostic control, **not** an operation performed by every cursor movement.

Ghost CPU frames use the shared 1100×720 renderer, with visibility/projection
assertions after font/viewport setup. Width reflow includes rewrapping the source
document. Plain and ghost frames contain different text; subtracting them would
not isolate the incremental cost of drawing a ghost preview.
