# Cold Find and worker computation — 2026-09-08

Follow-up to the [September Find profiling target](2026-09-07-current.md#findings-and-next-profiling-targets).
Dense matching is the expensive case, not every scan of a large document. The
worker's overview projection is also significant. No application behavior was
changed in this profiling increment.

The [overview follow-up](2026-09-08-find-overview.md) implements and measures
incremental chunk traversal; this report preserves the pre-change baseline.

## Method

```sh
CARGO_TARGET_DIR=/tmp/token-managed-server-check.5prvI4 \
  CARGO_BUILD_JOBS=1 just profile-workloads find-cold
```

Production source at `8a5b751`; the only Rust change adds modes to the existing
`benches/editor_workloads.rs` probe. SHA-256 of that measured fixture:
`f6804a3f937fa20e7fa4bf9ad3d236151a5a965f522a1219718144fbe423156a`.
Apple M2 Max, macOS 15.6 (24G84), Rust 1.98.0 (`88d9e12ae`), native ARM64,
optimized Cargo bench profile (opt-level 3, thin LTO), default features.

Each document has 10,000 or 100,000 repetitions of `ordinary text on a short line`
plus a final `final_marker` line. Queries use default case-insensitive literal
search: `ordinary` matches every repeated line, `final_marker` matches once at
the end, and `missing_marker` never matches. Match counts are asserted outside
timing. Ten warmups precede 100 observations for each stage/case.

- **Cold:** a fresh Find state and `matches(document)` each time, including
  query compilation, Rope flattening, matching, character-offset conversion,
  result allocation and destruction. No cached match list is reused.
- **Worker:** a production request obtained from update, then fresh `compute()`
  results each time. Includes the scan plus logical overview-line construction;
  excludes request creation, thread scheduling, reply dispatch and rendering.

These are warm-process, cold-result-cache CPU measurements, not cold disk reads,
native key-to-display latency or allocation profiles. Compilation and regression
checks finished before the timed results and sampling. The independent repeat
ran after the two CPU samples, with no source changes. The desktop was active
and not load-controlled. The existing release-only `revision` warning remains.

Dense 100,000-line p95 was 7.625/7.478 ms for cold scans and 12.182/11.481 ms
for worker computation. These repeats establish a useful local workload, not
tail-latency guarantees. Differences between cold/worker timings for sparse and
absent queries are small run variation, not evidence that adding work is faster.

## CPU attribution and next action

`sample-find-cold` and `sample-find-worker` run their dense 100,000-line stage for
12 seconds and print the child PID. Attach `/usr/bin/sample PID 5 1 -file PATH`
from another terminal. Both samples below used the same optimized executable;
Rust symbols are mangled but retain identifiable function names. Inlining means
these are sampled stack attributions, not exact independently timed stages.

- Cold scan: 3,813 main-thread samples. A regex search subtree accounts for
  2,852 (~75%), with DFA forward/reverse search and its literal prefilter prominent.
  The Rope-to-string formatting branch has 194 (~5%); query construction has
  53 (~1.4%). A query cache alone would not address the dominant dense cost.
- Worker: 3,858 main-thread samples. Overview initialization accounts for
  1,398 (~36%), including 1,087 samples beneath Rope line iteration. The main
  match-computation branch accounts for 2,434 (~63%). This corroborates the
  roughly 4 ms additional dense-worker time; it is not a synchronization wait.

The next warranted experiments are a narrowly gated literal-search fast path
and a cheaper overview projection. Both must preserve Unicode case folding,
character offsets, regex/whole-word semantics and Rope newline behavior. This
report does **not** implement or validate either optimization. It does not justify
a new worker, result cache or UI scheduling API. Existing asynchronous display
and fresh explicit-navigation semantics remain intact.
