I just finished consolidating the CSV editor design documentation. The gap analysis doc was merged into the main design doc and deleted.

Design decisions resolved:
- State preservation: Discard state on toggle, re-parse each time (stateless approach)
- Auto-enable: No auto-enable. Manual toggle via command palette "Toggle CSV View" only
- Size limits: No hard limits, implementation should handle large files with virtual scrolling
- Internal delimiter (0xFA): Accepted risk for memory efficiency, re-assess if issues arise

Key implementation details from the spec:
- ViewMode enum in EditorState: Text (default) or Csv(CsvState)
- CsvState contains: CsvData, selected_cell, viewport, editing state, column_widths, delimiter
- Memory-efficient storage: Each row stored as single delimited string (0xFA delimiter) instead of Vec<Vec<String>>
- Uses csv crate (1.3) for RFC 4180 compliant parsing
- Keymap integration needed: add csv_mode context condition, CsvToggle command, etc.
- Theme fallback: CsvTheme should derive defaults from existing gutter/editor theme fields

Implementation phases from spec:
- Phase 1: Read-only viewer (CsvState, CsvData, parsing, grid rendering, cell navigation, toggle command)
- Phase 2: Cell editing (CellEditState, cell editor, sync to document buffer, undo/redo)
- Phase 3: Polish (performance, virtual scrolling, mouse click, copy)

Module structure planned:
- src/csv/mod.rs, parser.rs, model.rs, viewport.rs, navigation.rs, editing.rs, render.rs

Testing: Spec includes comprehensive unit tests, integration tests, stress tests (1K-500K rows), and render tests.

Documentation workflow I established:
- Design docs in docs/feature/*.md for planned/active features
- Completed feature docs move to docs/archived/
- ROADMAP.md tracks completed and planned work
- CHANGELOG.md has release notes
