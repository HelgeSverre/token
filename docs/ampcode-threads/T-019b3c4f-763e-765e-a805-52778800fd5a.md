### A. Fix/verify `Document::{find_all_occurrences, find_next_occurrence}`

**1. Define index semantics and enforce them (chars, not bytes)**

Everywhere else in `Document` you’re using **character indices**:

- `len_chars`, `line_to_char`, `offset_to_cursor`, `cursor_to_offset` all operate in char-space.
- Tests call `find_next_occurrence("abc", 5)` where `5` is an offset in the same conceptual units as cursor/selection.

Implementation outline:

```rust
impl Document {
    pub fn len_chars(&self) -> usize {
        self.buffer.len_chars()
    }

    pub fn find_all_occurrences(&self, needle: &str) -> Vec<(usize, usize)> {
        let mut results = Vec::new();
        if needle.is_empty() {
            return results;
        }

        let needle_chars: Vec<char> = needle.chars().collect();
        if needle_chars.is_empty() {
            return results;
        }

        let haystack_len = self.buffer.len_chars();
        let mut pos = 0;

        // Simple char-based scan, non-overlapping matches
        while pos + needle_chars.len() <= haystack_len {
            if self.match_at(pos, &needle_chars) {
                let start = pos;
                let end = pos + needle_chars.len();
                results.push((start, end));
                pos = end; // non-overlapping
            } else {
                pos += 1;
            }
        }

        results
    }

    pub fn find_next_occurrence(&self, needle: &str, start: usize) -> Option<(usize, usize)> {
        if needle.is_empty() {
            return None;
        }
        let needle_chars: Vec<char> = needle.chars().collect();
        if needle_chars.is_empty() {
            return None;
        }

        let haystack_len = self.buffer.len_chars();
        if haystack_len == 0 {
            return None;
        }

        // Clamp start to [0, haystack_len)
        let start = start.min(haystack_len.saturating_sub(1));

        // Search [start, end)
        if let Some((s, e)) = self.find_in_range(&needle_chars, start, haystack_len) {
            return Some((s, e));
        }
        // Wrap: search [0, start)
        self.find_in_range(&needle_chars, 0, start)
    }

    fn match_at(&self, pos: usize, needle: &[char]) -> bool {
        for (i, &c) in needle.iter().enumerate() {
            if self.buffer.char(pos + i) != c {
                return false;
            }
        }
        true
    }

    fn find_in_range(
        &self,
        needle: &[char],
        start: usize,
        end: usize,
    ) -> Option<(usize, usize)> {
        let n = needle.len();
        if n == 0 || end <= start || end - start < n {
            return None;
        }
        let mut pos = start;
        while pos + n <= end {
            if self.match_at(pos, needle) {
                return Some((pos, pos + n));
            }
            pos += 1;
        }
        None
    }
}
```

---

3) Rationale and trade-offs

- **Char-based search** aligns with the rest of your model and prevents Unicode bugs. Anything byte-based will drift out of sync with `Cursor` and selections once non-ASCII is involved.
- **Non-overlapping matches** keep replace logic easy and predictable.
- Keeping search logic primarily in `Document` keeps the UI thin and avoids duplicating search behavior in different places.

Alternatives:

- Search on `String` copies of the whole document (simpler) and then convert byte offsets to char offsets; this is easy but can be O(n²) for multiple matches and error-prone with multi-byte chars. Not worth it given `ropey` already gives you char access.

---

4) Risks and guardrails

- **Risk: Incorrect index units** – If any part of the code still treats offsets as bytes, selections and cursor jumps will break on Unicode.
  - Guardrail: write explicit Unicode tests and assert `offset_to_cursor(cursor_to_offset(...))` consistency around found locations.
- **Risk: inconsistent “start” semantics for find-next** – If different callers pass different offsets (cursor start vs selection end), behavior will feel inconsistent.
  - Guardrail: centralize “compute search start offset” in one helper and document it.
- **Risk: unused flags (`case_sensitive`, `replace_mode`)** – They will confuse future maintainers.
  - Guardrail: either wire them now, or remove them until you’re ready.

---

5) When to consider the advanced path

Revisit the design if:

- Files get very large (tens/hundreds of MB) and search becomes sluggish.
- You want incremental search, regex, or multi-cursor-aware replace.
- You want to highlight all matches live as the user types in the query box.

---

6) Optional advanced path (brief)

Later, you could:

- Introduce a `SearchState` in the model (last query, last match range, all match positions for highlighting).
- Support regex or whole-word search with a `SearchOptions` struct.
- Cache results and invalidate them only on `Document::revision` changes.

For now, implementing the char-based `find_*` correctly, adding Unicode/edge-case tests, and wiring `FindReplaceState` through `ModalMsg::Confirm` with case sensitivity will give you a correct, predictable find behavior with minimal complexity.
