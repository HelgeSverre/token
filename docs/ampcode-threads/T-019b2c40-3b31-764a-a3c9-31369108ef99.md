Current task: Cursor icon handling cleanup
- The sidebar currently shows the I-beam (text edit) cursor when hovering, but should show the default pointer
- The text cursor (I-beam) should only appear when hovering over text editor areas
- Resize cursors should appear on splitters and sidebar resize handles

Key cursor handling location:
- src/runtime/app.rs has update_cursor_icon() function (around line 248) that handles cursor changes based on mouse position
- It currently sets CursorIcon::Text for editor area, CursorIcon::Default for status bar and tab bars, and CursorIcon::ColResize/RowResize for splitters
- Sidebar is not explicitly handled in update_cursor_icon() - it falls through to Text cursor

Cursor areas that need handling:
- Sidebar file tree: Default pointer
- Sidebar resize border (right edge): ColResize
- Tab bar: Default pointer (already handled)
- Status bar: Default pointer (already handled)
- Splitters: ColResize/RowResize (already handled)
- Editor text area: Text/I-beam cursor
- Modal overlays: Default pointer

The sidebar width is calculated via workspace.sidebar_width(scale_factor) and the sidebar renders from x=0.

3) Rationale and trade-offs

- **Explicit focus is simpler and correct**: focus is a single, global concept (`FocusTarget`), instead of being inferred from selection, visibility, or ad-hoc checks.
- **Keeps Elm-ish structure** but doesn’t overcomplicate: we add one enum and one field in `UiState`, and reuse existing routing functions.
- **Minimal changes where behavior is wrong**:
  - `KeyContext` now reflects explicit focus.
  - `is_sidebar_focused` no longer conflates “has selection” with “has focus”.
  - Mouse click behavior now consistently updates focus.
- **Avoids large pipeline refactor**: we don’t rewire keymap vs. `handle_key` ordering; existing keymap logic remains, but can now rely on correct context flags.

Alternative (heavier) design would be to centralize *all* key routing in a single dispatcher (focus → route → keymap/editor/etc.). That’s more invasive and not necessary yet.

---

4) Risks and guardrails

- **Keybindings that ignore focus conditions**: if your keymap has bindings that don’t specify `EditorFocused` / `SidebarFocused`, they may still fire regardless of focus.
  - Guardrail: for any editor-only keys (arrows, text navigation), add an `EditorFocused` condition to the keymap. For sidebar-specific keys, add `SidebarFocused`.
- **Modal consistency bugs**: if any code manipulates `active_modal` directly instead of using `UiState::open_modal` / `close_modal`, `focus` could get out of sync.
  - Guardrail: consolidate modal open/close through those helpers; avoid setting `active_modal` directly.
- **Sidebar hidden while focused**: if the sidebar is focused and you hide it, focus still says `Sidebar`.
  - Guardrail: in the handler that hides the sidebar (`WorkspaceMsg::ToggleSidebar` or similar), if `focus == Sidebar`, set it back to `Editor`.

---

5) When to consider the advanced path

Revisit the design if:

- You introduce more focusable regions (status bar commands, embedded terminals, search panels, etc.).
- You want keymaps that are fully declarative with focus-based routing (e.g., different bindings per region without manual routing in `handle_key`).
- You need “focus stacks” (e.g., nested widgets where ESC pops back to a previous focus target, not always the editor).

---

6) Optional advanced path (outline only)

If/when you need more, evolve to:

- `FocusTarget` with more variants (e.g., `StatusBar`, `Terminal`, `EditorGroup(GroupId)`).
- A small `FocusManager` on `UiState`:

  ```rust
  pub struct FocusManager {
      current: FocusTarget,
      previous: Option<FocusTarget>,
  }
  ```

  with methods like `set(FocusTarget)`, `restore_previous()`, `is(T)`, etc.

- A unified key dispatcher that *first* checks `FocusTarget` and routes:
  - `Modal` → modal handler (no keymap).
  - `Sidebar` → sidebar handler; if not consumed, optionally keymap with `SidebarFocused`.
  - `Editor` → keymap + editor fallback / CSV.

For now, the simpler explicit `FocusTarget` + UI updates on mouse/keyboard is enough to fix your current issues and gives you a clean base to extend later.

### Focus Management System Summary

#### Problem
The sidebar had keyboard navigation code but couldn't actually capture focus - clicking on items selected them but didn't change keyboard routing. Arrow keys still moved the editor cursor even when a sidebar item was selected.

#### Solution
Implemented an explicit `FocusTarget` enum with proper focus tracking:

**New Types:**
- `FocusTarget` enum: `Editor`, `Sidebar`, `Modal`
- Stored in `UiState.focus`

**Focus Transfer Rules:**
1. **Click on sidebar** → Focus transfers to `Sidebar`
2. **Click outside sidebar** (editor, splitters, tabs, status bar) → Focus goes to `Editor`
3. **Open modal** → Focus goes to `Modal` (via `UiState::open_modal()`)
4. **Close modal** → Focus returns to `Editor` (via `UiState::close_modal()`)
5. **Hide sidebar while focused** → Focus returns to `Editor`
6. **Escape in sidebar** → Focus returns to `Editor`

**KeyContext:**
- `editor_focused` and `sidebar_focused` now derive from `UiState.focus` instead of being inferred from selection state

**Keyboard Routing:**
- `is_sidebar_focused()` in input.rs now checks `FocusTarget::Sidebar`
- Sidebar keyboard navigation (arrows, Enter, Space) only works when sidebar actually has focus

This provides a clean, explicit focus model that can be extended to support more focusable regions (terminal panels, search panels, etc.) in the future.
