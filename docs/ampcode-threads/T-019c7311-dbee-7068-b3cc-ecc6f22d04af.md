## Assistant

The `SetCursorPosition` handler always calls `ensure_cursor_visible()` with `ScrollRevealMode::Minimal`. The core question is: **should clicking on a visible line trigger `ensure_cursor_visible` at all?**

In VS Code and most other editors, clicking on a visible line **never** scrolls the viewport. The scroll-into-view logic is only needed when the cursor moves to a position that isn't currently visible. A click on a visible line, by definition, places the cursor on a visible position.

The fix should be: **don't call `ensure_cursor_visible()` for mouse clicks that land on already-visible lines.** The `pixel_to_cursor` function already constrains the line to the document bounds, and since the click happened on a visible line, the cursor is guaranteed to be visible.

But wait — there's a subtlety. With `scroll_padding = 1`, clicking on the very last visible line WOULD trigger scrolling (since that line is outside the "safe zone"). Some editors do this (scroll the viewport slightly when you click near the edge), but many don't apply scroll margins to mouse clicks — only to keyboard navigation.

Let me verify the complete theory by checking if there could be an off-by-one in the line computation. Let me trace through an example:

Suppose:
- `visible_lines = 30`
- `top_line = 0`
- `scroll_padding = 1`
- User clicks on visual line 29 (the last rendered line = document line 29)

Then in `ensure_cursor_visible_with_mode`:
- `safe_top = 0 + 1 = 1`
- `safe_bottom = 0 + 30 - 1 - 1 = 28`
- `cursor.line = 29`
- `off_below = 29 > 28` → **true**
- Scroll: `top_line = 29 + 1 + 1 - 30 = 1`

So clicking the last visible line scrolls down by 1 line. That's expected with padding=1. But the user reports scrolling when clicking at the "midpoint-ish." This means either:

1. `visible_lines` is significantly wrong (too small), OR
2. There's some other path that uses a different scroll mode
