I implemented the Markdown Preview feature (F-170) for Token Editor. Here's what I built:

What was implemented:
- Added pulldown-cmark and wry dependencies to Cargo.toml
- Created src/markdown/ module with renderer.rs (markdown to HTML), theme.rs (preview colors), and preview.rs (PreviewPane state)
- Added LayoutNode::Preview variant and PreviewId type to the layout tree system
- Added preview pane storage (previews HashMap) to EditorArea with management methods: open_preview_for_document(), close_preview(), toggle_focused_preview()
- Added PreviewMsg enum (Toggle, Open, Close, Refresh, ScrollToLine, SyncFromPreview, ToggleSync) to messages.rs
- Added update/preview.rs handler that toggles preview via editor_area methods
- Added native markdown preview rendering in view/mod.rs with basic styling (headings, code blocks, lists, links)
- Added MarkdownTogglePreview and MarkdownOpenPreviewToSide commands with Cmd+Shift+V keybinding

Key patterns I followed:
- Elm-style architecture: messages flow through update functions
- Layout tree uses LayoutNode enum (Empty, Group, Split, Preview) for recursive layout computation
- Preview panes are stored in EditorArea.previews HashMap with PreviewId keys
- Rendering iterates over both groups and previews in render_editor_area()

What still needs to be done (from the design doc):
- Scroll synchronization between source editor and preview
- Auto-refresh on document edits with debouncing
- Close preview when switching away from markdown file
- Enhanced markdown rendering (bold/italic, nested lists, tables)
- The rendered_lines field in PreviewPane is unused - could support richer native rendering

Important technical details:
- Document content accessed via document.buffer (Rope type), not a rope() method
- PreviewPane has scroll_offset for scrolling, scroll_sync_enabled flag, last_revision for tracking changes
- The markdown/renderer.rs has add_line_markers() for scroll sync data-line attributes in HTML output
- CSS and JS for scroll sync are already in the HTML template (scrollToLine function, scroll event listener)

## Assistant

Now I understand the architectural challenge. Token uses:
- `winit` for window management
- `softbuffer` for CPU-based pixel rendering (the entire window is a pixel buffer)

To integrate `wry` webview, we need to either:
1. **Create a child webview** - The webview would overlay part of the window
2. **Manage bounds** - Keep the webview's position/size in sync with the preview pane's rect

The key insight is that `wry::WebViewBuilder::build_as_child(&window)` creates a native child window that overlays the parent. This means we need to:

1. Create the webview when opening preview
2. Position it to match the preview pane's rect
3. Update its bounds whenever the layout changes
4. Update its HTML content when the document changes
5. Destroy it when closing preview

- [src/runtime/webview.rs](file://~/code/token-editor/src/runtime/webview.rs) - `WebviewManager` struct that manages `wry::WebView` instances

#### Key Changes

**WebviewManager** ([webview.rs](file://~/code/token-editor/src/runtime/webview.rs)):
- `create_webview()` - Creates a wry child webview with HTML content
- `update_content()` - Updates webview HTML via JavaScript injection
- `update_bounds()` - Repositions webview when layout changes
- `close_webview()` - Removes webview when preview closes
- `scroll_to_line()` - For scroll synchronization (prepared for future use)

**App Integration** ([app.rs](file://~/code/token-editor/src/runtime/app.rs#L1180-L1270)):
- Added `webview_manager: WebviewManager` field to `App` struct
- Added `sync_webviews()` method called after each render
- Syncs webviews with model's preview panes:
  - Creates webviews for new previews
  - Updates bounds on resize
  - Updates HTML content when document revision changes
  - Destroys webviews when previews close

#### How It Works
1. User presses `Cmd+Shift+V` → `PreviewMsg::Toggle` → Preview pane created in model
2. On next render → `sync_webviews()` detects new preview → Creates `wry::WebView` with rendered HTML
3. User edits document → Document revision increments → `sync_webviews()` updates webview content
4. User closes preview → Preview removed from model → `sync_webviews()` destroys webview

#### Architecture
- **Native rendering** still happens via softbuffer (fallback/background)
- **Webview** overlays on top as a native OS child window
- Uses `wry::WebViewBuilder::build_as_child()` to embed in winit window
