### 2.5. Handling `ContextMenuMsg` in update()

In your `update` function ( Elm-style), add a branch for `Msg::Ui(UiMsg::ContextMenu(msg))`:

```rust
fn update_ui_context_menu(model: &mut AppModel, msg: ContextMenuMsg) -> Option<Cmd> {
    match msg {
        ContextMenuMsg::Open(req) => {
            let state = crate::context_menu::build_menu_for_request(model, &req);

            if state.items.is_empty() {
                model.ui.context_menu = None;
            } else {
                model.ui.context_menu = Some(state);
            }
            Some(Cmd::Redraw)
        }
        ContextMenuMsg::Close | ContextMenuMsg::Cancel => {
            model.ui.close_context_menu();
            Some(Cmd::Redraw)
        }

        ContextMenuMsg::MoveUp => {
            if let Some(menu) = &mut model.ui.context_menu {
                move_selection_vertical(menu, -1);
            }
            Some(Cmd::Redraw)
        }
        ContextMenuMsg::MoveDown => {
            if let Some(menu) = &mut model.ui.context_menu {
                move_selection_vertical(menu, 1);
            }
            Some(Cmd::Redraw)
        }
        ContextMenuMsg::MoveLeft => {
            if let Some(menu) = &mut model.ui.context_menu {
                pop_submenu(menu);
            }
            Some(Cmd::Redraw)
        }
        ContextMenuMsg::MoveRight => {
            if let Some(menu) = &mut model.ui.context_menu {
                open_submenu_if_any(menu);
            }
            Some(Cmd::Redraw)
        }

        ContextMenuMsg::Confirm => {
            if let Some(menu) = &mut model.ui.context_menu {
                if let Some(action) = current_item_action(menu) {
                    // Take the action, then close.
                    apply_menu_action(model, action);
                    model.ui.close_context_menu();
                } else {
                    model.ui.close_context_menu();
                }
            }
            Some(Cmd::Redraw)
        }

        ContextMenuMsg::HoverItem { path } => {
            if let Some(menu) = &mut model.ui.context_menu {
                menu.active_path = path;
            }
            Some(Cmd::Redraw)
        }

        ContextMenuMsg::ActivateItem { path } => {
            if let Some(menu) = &mut model.ui.context_menu {
                menu.active_path = path.clone();
                if let Some(action) = current_item_action(menu) {
                    apply_menu_action(model, action);
                }
                model.ui.close_context_menu();
            }
            Some(Cmd::Redraw)
        }
    }
}
```

Helper functions (pseudo-code):

```rust
fn navigate_to_path<'a>(items: &'a [MenuItem], path: &MenuPath) -> Option<(&'a [MenuItem], usize)> {
    let mut slice = items;
    let mut last_idx = None;

    for (depth, &idx) in path.iter().enumerate() {
        if idx >= slice.len() { return None; }
        last_idx = Some(idx);
        if depth + 1 == path.len() {
            break;
        }
        match &slice[idx].kind {
            MenuItemKind::Submenu { items } => {
                slice = items;
            }
            _ => return None,
        }
    }

    last_idx.map(|idx| (slice, idx))
}

fn current_item_action(menu: &ContextMenuState) -> Option<MenuAction> {
    let (slice, idx) = navigate_to_path(&menu.items, &menu.active_path)?;
    match &slice[idx].kind {
        MenuItemKind::Action(a) if slice[idx].enabled => Some(a.clone()),
        _ => None,
    }
}

fn apply_menu_action(model: &mut AppModel, action: MenuAction) {
    match action {
        MenuAction::Messages(msgs) => {
            for msg in msgs {
                let _ = crate::update::update(model, msg);
            }
        }
        MenuAction::None => {}
    }
}

// Move selection within the current sibling list.
fn move_selection_vertical(menu: &mut ContextMenuState, delta: i32) {
    if menu.items.is_empty() { return; }

    let mut path = if menu.active_path.is_empty() {
        vec![0]
    } else {
        menu.active_path.clone()
    };

    // Work on the deepest level.
    if let Some((slice, idx)) = navigate_to_path(&menu.items, &path) {
        let len = slice.len() as i32;
        let mut new_idx = idx as i32;
        loop {
            new_idx = (new_idx + delta).rem_euclid(len);
            if matches!(
                slice[new_idx as usize].kind,
                MenuItemKind::Action(_) | MenuItemKind::Submenu { .. }
            ) && slice[new_idx as usize].enabled
            {
                path.last_mut().map(|p| *p = new_idx as usize);
                break;
            }
        }
        menu.active_path = path;
    } else {
        menu.active_path = vec![0];
    }
}

fn pop_submenu(menu: &mut ContextMenuState) {
    if menu.active_path.len() > 1 {
        menu.active_path.pop();
    }
}

fn open_submenu_if_any(menu: &mut ContextMenuState) {
    if let Some((slice, idx)) = navigate_to_path(&menu.items, &menu.active_path) {
        if let MenuItemKind::Submenu { items } = &slice[idx].kind {
            if !items.is_empty() {
                menu.active_path.push(0);
            }
        }
    }
}
```

### 2.7. Mouse hit-testing and rendering

Render and hit-test like you handle modals:

- In `Renderer::render(...)`, if `ui.context_menu.is_some()`:
  - Compute the menu panel rect starting at `anchor`.
  - Lay out items as a vertical list (height from `line_height` or a menu-specific metric).
  - For submenus, render another panel offset to the right of the parent item’s rect.

- For hit-testing:
  - Add a helper `fn hit_test_context_menu(&self, ui: &UiState, x: f64, y: f64) -> Option<MenuPath>`.
  - In `WindowEvent::MouseInput` for left-click:
    - If a context menu is open:
      - Call `hit_test_context_menu`.
      - If `Some(path)`, send `UiMsg::ContextMenu(ContextMenuMsg::ActivateItem { path })`.
      - If `None`, close the menu: `UiMsg::ContextMenu(ContextMenuMsg::Close)`.

- For hover:
  - In `WindowEvent::CursorMoved`, when `ui.context_menu.is_some()`:
    - Call `hit_test_context_menu`.
    - If `Some(path)`, send `HoverItem { path }` to update highlight and open submenus on hover (optional: with a small delay).
    - Also update cursor icon (pointer vs normal).

This keeps geometry in the view layer and state in `UiState`, matching how you already map pixels -> logical editor actions.

3) Rationale and trade-offs

- **Reuse existing abstractions**: Menus trigger `Msg` (and often use `Command::to_msgs`), so they integrate cleanly with the current Elm-style loop.
- **Context-sensitive**: `ContextMenuTarget` captures just enough info (selection, path, tab id, etc.) for region-specific builder functions to create dynamic menus.
- **Scalable**: Menu items are a tree with `MenuItemKind::Submenu`; navigation uses `active_path` so nesting is arbitrary without extra data structures.
- **Minimal coupling**: Runtime (`app.rs` + `Renderer`) only does hit-testing and invokes `ContextMenuMsg::*`; business logic resides in `update`/builders.
- **Keyboard-friendly**: Simple interception for arrows/Enter/Escape gives full keyboard navigation without complicating the keymap system.

Alternatives like embedding context menu logic directly into each region’s update code or adding menu-specific `Command` variants would either be more scattered or require more invasive changes to keymap + dispatch.

---

4) Risks and guardrails

- **Geometry drift**: If menu layout and hit-testing are implemented separately, they can get out of sync.
  - Guardrail: put hit-testing in the same module / functions that compute drawing rects (like your modal geometry helpers).
- **State leaks**: Forgetting to close menus on actions (e.g., switching tabs via keyboard).
  - Guardrail:
    - Always close the menu after `Confirm`/`ActivateItem`.
    - Optionally close on any click outside and on global focus changes (e.g., when a modal opens).
- **Region proliferation**: Too many special cases in `build_menu_for_request`.
  - Guardrail: keep one “builder per region” function and only add new variants when you truly need new menu types.

---

5) When to consider the advanced path

Revisit the design if:

- You want **searchable menus** (type-to-filter within the context menu), which may require adding an `EditableState` to `ContextMenuState`.
- You plan to support **multiple simultaneous popups** (tooltips + menu + modal overlays), which could justify a more generic “popup manager” abstraction.
- You need **platform-native menus** (e.g. macOS NSMenu) instead of custom-drawn; that would move action dispatching closer to OS APIs and partially bypass your Elm loop.

Created the spec at [docs/feature/context-menu.md](file://~/code/token-editor/docs/feature/context-menu.md).

**Key design decisions:**

1. **Flat menus only** (no submenus in V1) - simpler implementation
2. **`ContextMenuState`** stored in `UiState` alongside modals but separate
3. **`MenuAction::Messages(Vec<Msg>)`** - supports both `Command`-based and custom actions
4. **`ShortcutHintProvider`** - queries the live `Keymap` so user customizations are reflected
5. **Keyboard interception** happens before normal keymap when menu is open (arrows/Enter/Escape)
6. **`KeyContext` extension** with `context_menu_active` for conditional keybindings if needed

The spec covers 5 phases, with file operations (rename/delete/etc.) deferred to Phase 5.
