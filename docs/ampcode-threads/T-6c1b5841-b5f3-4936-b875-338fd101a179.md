Added per-cursor primitives like move_cursor_left_at(doc, idx) and all-cursors wrappers like move_all_cursors_left(doc) to EditorState.

I also discovered that Expand/Shrink Selection was already implemented (Option+Up/Down) with 18 tests in tests/expand_shrink_selection.rs.

Key architectural patterns I followed:
- EditorState has cursors: Vec<Cursor> and selections: Vec<Selection> (parallel arrays, invariant: cursors[i].to_position() == selections[i].head)
- Multi-cursor editing processes cursors in reverse document order to avoid offset shifting issues (cursors_in_reverse_order helper exists)
- After multi-cursor operations, call deduplicate_cursors() to handle collisions
- Each cursor preserves its own desired_column for vertical movement through ragged lines
- Batch operations use EditOperation::Batch for atomic undo/redo

The codebase uses Elm Architecture: Msg -> update() -> Cmd -> render. Messages are in src/messages.rs (EditorMsg, DocumentMsg, etc.), handlers in src/update.rs.

## 3) Rationale and trade-offs

- **SelectAll as single selection**:
  - Pros: matches user mental model; avoids weird multi-cursor “select all lines independently” semantics.
  - Cons: drops existing multi-cursors, but that’s standard and quickly rebuilt via `SelectAllOccurrences` / `SelectNextOccurrence`.

- **Merging overlapping selections**:
  - Pros: simplifies multi-cursor editing logic; prevents double edits; implements the design doc’s explicit intent.
  - Cons: Slightly more complexity in `EditorState`, but localized and testable.

- **Per-cursor `SelectWord` / `SelectLine` with normalization**:
  - Pros: intuitive – each caret acts locally; user can select multiple words or lines quickly.
  - Cons: Slight extra work to handle unicode + char_type, but you already have the utilities and tests.

- **ExtendSelectionToPosition collapsing multi-cursor**:
  - Pros: simple, predictable; avoids ambiguous “extend all” semantics.
  - Cons: If someone really wanted Shift+Click to extend multiple selections, they don’t get that; but that’s very uncommon.

- **Expand/Shrink single-cursor only**:
  - Pros: keeps selection history manageable; defers non-essential complexity.
  - Cons: Slight inconsistency with JetBrains which can expand multiple carets, but a minor feature gap.

## 4) Risks and guardrails

**Risks**

- `merge_overlapping_selections()` might accidentally:
  - Break the cursor/head invariant.
  - Mis-handle cross-line merges (e.g., due to incorrect `Position` ordering).
- Misaligned expectations around `ExtendSelectionToPosition` in multi-cursor scenarios.
- Unicode edge cases in `SelectWord` (especially surrogate pairs or grapheme clusters) – but you’re already operating on `char`s, so behavior is consistent with rest of editor.

**Guardrails**

- Unit tests for `merge_overlapping_selections()` covering multi-line and adjacency.
- Tests asserting invariants:
  - After `SelectWord`, `SelectLine`, `SelectAll`, `ExtendSelectionToPosition`:
    - `cursors.len() == selections.len()`.
    - `cursor[i].to_position() == selection[i].head`.
- Keep `merge_overlapping_selections()` **purely structural**:
  - No I/O or side effects beyond `cursors`/`selections` arrays.
- Avoid calling merge in very hot paths unnecessarily; use only before edits / after selection-creation.
