I am implementing workspace management for a Rust text editor with an Elm-style architecture (messages, update handlers, commands).

Current issue: Editor area hit testing is not offset by the sidebar width. Clicks in the editor area use absolute window coordinates instead of being converted to local coordinates relative to the editor region. This causes clicks to be misaligned when the sidebar is visible.

What I discovered about the coordinate system:
- Mouse coordinates from winit are in physical pixels (already scaled)
- All metrics (file_tree_row_height, tab_bar_height, etc.) are pre-scaled by scale_factor in ScaledMetrics
- The sidebar renders from x=0, y=0 of the window
- The editor area starts at x=sidebar_width, y=0
- The view/geometry.rs module has pixel_to_cursor() which converts pixel coords to document line/column, but it doesn't account for sidebar offset
- Frame in view/frame.rs provides drawing primitives but doesn't track region offsets

The architectural goal: Create a "region" abstraction where each render area (sidebar, modal, editor group, etc.) can convert clicks to local coordinates. This would:
- Store the region's position within the parent/window
- Convert absolute window coordinates to region-local coordinates
- Allow hit testing to work correctly regardless of layout changes

Relevant patterns:
- Rendering uses Frame for drawing primitives
- Editor groups have their own tab bars and content areas
- pixel_to_cursor_in_group() exists in geometry.rs but takes group_rect as parameter
- The sidebar hit testing I fixed works correctly because it checks if x < sidebar_width first

Key files for coordinate handling:
- src/view/geometry.rs - pixel_to_cursor() and related functions
- src/view/frame.rs - Frame struct for drawing
- src/runtime/app.rs - mouse event handling
- src/view/mod.rs - Renderer and render functions

The fix likely needs to:
1. Pass sidebar_width to mouse handling code in app.rs
2. Offset mouse coordinates by sidebar_width before calling pixel_to_cursor
3. Or create a proper region/viewport abstraction that handles this automatically

there is a remaining bug realted to hit testing inside editor areas, they are not offset by the size of the sidebar, meaning we are operating on absolute window positioning, but we need each seperate render-area (sidebar, modal, textarea, split container etc to convert clicks inside of it to local positions, currently clicking in the editorarea still thinks that the editorarea is positioned relative to top-left of window, but when sidebar is there, this has to change, we need to investigate a proper archeitectual fix so that these kinds of issues are easier to do, this was what the viewprot geometry and frame stuff was meant to do for us, create a "region" where positions could use logical offsets and all of these things would be correclty computed and offset based on the region positioning , consult oracle, review the ui rendering code, use search and librarian subagents to figure out a comprehensive solution to this issue and implement the fix throughout all rendering code

3) Rationale and trade‑offs

- **Minimizes code changes:**
  You don’t touch call sites in `app.rs` (other than existing focus logic) or the rendering code. The only behavioral change is inside `geometry.rs` where hit‑testing was already meant to live.

- **Split‑view correctness by construction:**
  `group.rect` is already the canonical layout result from `compute_layout_scaled`, including:
  - Sidebar offset (`available_rect` starting at `x = sidebar_width`)
  - Split offsets (horizontal and vertical)
  Anything that renders text uses `group_rect`; hit‑testing now uses the same rects.

- **Future layout changes are localized:**
  If you add:
  - A right sidebar,
  - A top toolbar,
  - A bottom panel shrinking the editor area,
  as long as `EditorArea::compute_layout_scaled` continues to set `group.rect` in window coordinates, no changes are needed in hit‑testing. You don’t have to thread new “offset” parameters through every mouse handler.

- **Avoids ad‑hoc sidebar_width plumbing:**
  Passing `sidebar_width` into `pixel_to_cursor` would fix the *current* left sidebar, but break as soon as:
  - You have asymmetric layouts,
  - Groups don’t all share the same x offset (right splits),
  - Or the editor area moves vertically.
  Using `group.rect` avoids re‑encoding layout logic in hit‑testing.

- **Consistent with existing design:**
  `pixel_to_cursor_in_group` and `group_content_rect_*` already expect per‑group rects and perform local‑coordinate calculations. You’re just making the global helpers into thin wrappers around the group‑aware variants.

Alternative (what you’re not doing): passing `sidebar_width` or “editor area origin” down into `pixel_to_cursor`. That’s simpler in the short term but:

- Would still be wrong for horizontal splits (different `x` per group).
- Couples hit‑testing to current sidebar implementation instead of to the actual layout tree.
- Becomes hard to reason about as layouts get more complex.

- **Assumption: focused editor == editor in focused group.**
