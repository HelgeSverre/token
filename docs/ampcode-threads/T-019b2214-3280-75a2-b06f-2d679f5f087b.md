### Theme Loading Plan

#### Current State
- 4 built-in themes embedded at compile time (`BUILTIN_THEMES` array)
- `Theme::from_builtin(id)` loads by id (e.g., "default-dark")
- `Theme::from_yaml(yaml_str)` parses YAML string
- ThemePicker modal only shows built-in themes
- No file-based loading or user config support

#### Proposed Design

**Loading Priority** (mirrors keymap pattern):
1. **User config**: `~/.config/token-editor/themes/{id}.yaml`
2. **Project-local**: `./themes/{id}.yaml`
3. **Embedded**: Built-in themes compiled into binary

**Key Differences from Keymaps**:
- Themes don't merge — they replace entirely
- Theme picker should show all available themes (user + builtin)
- User can create custom themes by adding YAML files

**New Functions in `src/theme.rs`**:
```rust
/// Get user themes directory (~/.config/token-editor/themes/)
pub fn get_user_themes_dir() -> Option<PathBuf>

/// Load theme by id with priority: user → project → builtin
pub fn load_theme(id: &str) -> Result<Theme, String>

/// Load theme from file path
pub fn from_file(path: &Path) -> Result<Theme, String>

/// List all available theme ids (user + builtin, deduplicated)
pub fn list_available_themes() -> Vec<ThemeInfo>

pub struct ThemeInfo {
    pub id: String,
    pub name: String,        // Display name from YAML
    pub source: ThemeSource, // User, Project, or Builtin
}

pub enum ThemeSource {
    User,
    Project,
    Builtin,
}
```

**Changes to ThemePicker**:
- Use `list_available_themes()` instead of `BUILTIN_THEMES`
- Show theme source indicator in picker (optional)
- Load via `load_theme(id)` instead of direct YAML parse

**Config Persistence** (future enhancement):
- Store selected theme id in `~/.config/token-editor/config.yaml`
- Load on startup

#### Implementation Steps

1. Add `get_user_themes_dir()` and `from_file()` to theme.rs
2. Add `load_theme(id)` with priority chain
3. Add `ThemeInfo` and `list_available_themes()`
4. Update ThemePicker to use new API
5. Add tracing for theme loading

#### File Structure
```
~/.config/token-editor/
├── keymap.yaml          # User keybindings
└── themes/
    └── my-theme.yaml    # User themes
```

3. **Understand what `save()` actually does**

   ```rust
   impl EditorConfig {
       pub fn config_path() -> Option<PathBuf> {
           get_config_dir().map(|dir| dir.join("config.yaml"))
       }

       pub fn save(&self) -> Result<(), String> {
           let path = Self::config_path()
               .ok_or_else(|| "No config directory available".to_string())?;

           if let Some(parent) = path.parent() {
               std::fs::create_dir_all(parent)
                   .map_err(|e| format!("Failed to create config directory: {}", e))?;
           }

           let content = serde_yaml::to_string(self)
               .map_err(|e| format!("Failed to serialize config: {}", e))?;

           std::fs::write(&path, content)
               .map_err(|e| format!("Failed to write config to {}: {}", path.display(), e))?;

           tracing::info!("Saved config to {}", path.display());
           Ok(())
       }

       pub fn set_theme(&mut self, theme_id: &str) -> Result<(), String> {
           self.theme = theme_id.to_string();
           self.save()
       }
   }
   ```

   - Any failure to create the directory or write the file is converted into an `Err(String)` and then logged in `ui.rs` via `tracing::warn!`.
   - There is no silent failure path: either it writes successfully or you get a warning.

---

3) Rationale and trade-offs

- The control flow in `ModalMsg::Confirm` → `ThemePicker` → `set_theme` → `save` is straightforward and correctly propagates errors.
- There’s no evidence in this code of a sandbox or permissions-only bug; any I/O issue would show up as a logged warning.
- The `dirs` crate is intentionally platform-specific; using it but then documenting only the Linux/XDG path is what caused the confusion.
- Changing the actual storage path to `~/.config` *only on macOS* would go against what `dirs` is trying to do and could break user expectations / conventions on macOS; better to align your docs with `dirs`.

---

4) Risks and guardrails

- **Risk:** Some users may already have created themes/configs under `~/.config/token-editor` following the current comments.
  **Mitigation:** Optionally, on startup, look for `~/.config/token-editor/config.yaml` and migrate it once to the new (correct) location if present.

- **Risk:** If the app is ever sandboxed as a macOS App Store app, writes to `$HOME/Library/Application Support/token-editor` may fail.
  **Mitigation:** Keep the error logging in place; if you start seeing `Failed to write config...` errors, you can add a sandbox-friendly path or entitlements then.

---

5) When to consider the advanced path

Consider a more complex design only if:

- You need strict adherence to XDG paths on all Unix-like systems including macOS, or
- You want to support multiple locations (XDG + platform-native) with migration, or
- You plan to ship both CLI and GUI builds with different storage expectations.
