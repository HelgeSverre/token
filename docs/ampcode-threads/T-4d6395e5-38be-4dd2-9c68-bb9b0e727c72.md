---

3) Rationale and trade-offs

- **Why this simple approach?**
  - Stays entirely in **pure Rust**; no winit, no OS windows, no threads or real filesystem I/O in the benchmarks.
  - Reuses your real types: `AppModel`, `Msg`, `Cmd::needs_redraw()`, and roughly the real per-pixel work.
  - Gives actionable numbers: “typing 1k chars in a 10k‑line file at 1080p costs X ns per keypress”, “scrolling costs Y µs per `PageDown`”.
- **Why not benchmark the real `App` event loop?**
  - Involves winit event loop, system timers, and softbuffer – all of which make the benchmark **non-deterministic**, flaky on CI, and sometimes impossible to run headless.
  - Difficult to isolate CPU costs from platform noise.

So the chosen path is: **measure just the core loop** you care about, with **deterministic, in-process code**.

---

4) Risks and guardrails

- **Bench/production divergence**: if `BenchRenderer` diverges too much from `Renderer`, numbers may drift.
  - Mitigation: implement `BenchRenderer` by literally copying the inner loops from `view.rs` or `rendering.rs`, and keep a comment saying “keep in sync with Renderer”.
- **Doc/model initialization cost**: if each bench re-creates a big model inside the timed section, you’ll measure setup, not steady-state.
  - Mitigation: set up the model **once per bench invocation** (as in the examples) and then loop the `Msg → update → render` path inside.
- **Allocation noise**: if `render_frame` allocates every time, you’ll be measuring allocation, not pixel math.
  - Mitigation: allocate the `Vec<u32>` buffer once in `BenchRenderer::new`, then reuse and fill it each frame (as in `clear_buffer_fill`).

---

5) When to consider the advanced path

Move beyond these simple benches if:

- You suspect **OS/window-system interactions** (vsync, presentation, softbuffer, DPI changes) dominate latency or jitter.
- You’re targeting **very high refresh rates** (120–240 Hz) and see unexplained dropped frames, even though core benchmarks say you’re fine.
- You want to measure **async I/O behavior** (e.g., does saving a huge file stall the UI?).

Those are signals that you may need to profile the **real running app** and/or build integration-style benchmarks.

---

6) Optional advanced path (outline only)

If you ever need closer-to-real measurements:

- Extract a **core “engine”** struct (e.g. `CoreApp`) that owns `AppModel` and exposes:
  - `fn handle_msg(&mut self, msg: Msg) -> Cmd`
  - `fn render_into(&mut self, buffer: &mut [u32])`
- Make `App` (the winit `ApplicationHandler`) a thin wrapper around this engine.
- Then:
  - Your benches can instantiate `CoreApp` directly and call `handle_msg` + `render_into` in tight loops.
  - The real app still uses the exact same code, so benches stay representative.

This is a bigger refactor (L–XL), so I’d defer it until the simpler `BenchRenderer`-based benches show you need more realism.

---

If you implement the suggested `update`+`Cmd::needs_redraw`+`BenchRenderer::render_frame` benches, you’ll have a much clearer, actionable view of your main Elm loop’s performance, while keeping your benchmark suite simple and robust.
