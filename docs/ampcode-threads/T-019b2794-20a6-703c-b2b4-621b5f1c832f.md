I just completed Phase 2 of the CSV Viewer feature, which is Cell Editing.

I implemented the following capabilities:
- Cell editing: I can now press Enter or start typing to edit the selected cell.
- Edit buffer management: I added a CellEditState struct to track the edit buffer, cursor position, and original value.
- Cursor navigation within cells: I can use Left/Right arrow keys, Home, and End to move the cursor inside the cell editor.
- Character input: I can insert characters, delete backward with Backspace, and delete forward with Delete.
- Confirm/Cancel edit: Enter confirms the edit and moves to the next row (or up if I press the Up arrow while editing), Tab confirms and moves to the next cell, and Escape cancels the edit.
- Document synchronization: When an edit is confirmed, I update the underlying document buffer with the new cell value, ensuring proper CSV escaping for values containing delimiters, quotes, or newlines.

Key implementation details and patterns I used:
- I added CellEditState and CellEdit structs to src/csv/model.rs.
- I added editing-related methods to the CsvState struct in src/csv/model.rs.
- I introduced new CsvMsg variants in src/messages.rs for all editing actions.
- I implemented the escape_csv_value function in src/csv/parser.rs to handle CSV escaping according to RFC 4180.
- I updated src/update/csv.rs to handle all the new CsvMsg variants and to manage the document synchronization logic using find_row_byte_range and find_field_byte_range.
- I refined the input routing in src/update/mod.rs and src/runtime/input.rs. The system now checks if I am in CSV mode AND if I am currently editing a cell to correctly route keyboard input. This was crucial for ensuring Enter commits the edit and arrow keys move the cursor within the cell rather than moving the cell selection.
- I added the rendering logic for the cell editor overlay and cursor in src/view/mod.rs.
- I updated the documentation in docs/feature/csv-editor.md and docs/CHANGELOG.md to reflect the completion of Phase 2.

All tests are passing, and the feature is fully integrated.

In `update_splitter_drag`:


### C. Slightly harden the global-to-local splitter mapping

The mapping itself is **correct**:

- `EditorArea::compute_layout_node`:
  - For each `Split` container with `N` children, it pushes `N-1` `SplitterBar`s (one between each pair of children), ordered in a depth-first traversal.
  - Each `SplitterBar` gets `index: i`, which is the index of the *left* child in `container.ratios`.

- `find_container_for_splitter`, `update_container_ratios`, and `restore_container_ratios`:
  - All use the same scheme: for each `Split`, treat its `splitter_count = children.len() - 1` as a contiguous global index block `[current_index, current_index + splitter_count)`, then recurse into children after incrementing `current_index += splitter_count`.

So the same “global index ⇨ owning container” partition is used consistently in all three functions. That’s good.

### D. Reduce duplication between `find_container_for_splitter`, `update_container_ratios`, `restore_container_ratios`

These three functions share nearly identical traversal logic and index bookkeeping:

- Compute `splitter_count`.
- Check whether `target_index` falls into this container’s block.
- Otherwise, increment `current_index` and recurse into children.

To simplify and reduce maintenance risk, extract a generic traversal helper with a closure:

```rust
fn visit_splitter_container_mut<F>(
    layout: &mut LayoutNode,
    target_index: usize,
    current_index: &mut usize,
    mut f: F,
) -> bool
where
    F: FnMut(&mut SplitContainer, usize) -> bool,
{
    match layout {
        LayoutNode::Group(_) => false,
        LayoutNode::Split(container) => {
            let splitter_count = container.children.len().saturating_sub(1);

            if target_index >= *current_index && target_index < *current_index + splitter_count {
                let local_idx = target_index - *current_index;
                return f(container, local_idx);
            }

            *current_index += splitter_count;

            for child in &mut container.children {
                if visit_splitter_container_mut(child, target_index, current_index, &mut f) {
                    return true;
                }
            }
            false
        }
    }
}
```

- `update_container_ratios` just becomes:

  ```rust
      visit_splitter_container_mut(layout, target_index, current_index, |container, local_idx| {
  ```

3) Rationale and trade-offs

- **Correctness**:
  - Global ↔ local index mapping: the way splitters are pushed in `compute_layout_node` and how `current_index` is advanced in the helpers line up; no off-by-one or nesting issue, even with deeply nested splits and 3+ children.
  - Ratio math: the “pair-wise adjustment while preserving `left+right`” approach is sound and keeps the container’s total ratio sum stable. Using the original ratios for each update avoids cumulative float drift.

- **Edge cases**:
  - Deeply nested splits and 3+ children in a container are handled correctly by the global indexing scheme.
  - The only real hazard is small containers where `2 * MIN_PANE_SIZE_PIXELS > container_size`; the recommended guard around clamp resolves that without needing a more complex size enforcement system.

- **Code organization**:
  - The current traversal logic is duplicated 3x; factoring a helper removes cognitive load and makes future changes safer.
  - The `SplitterDragState` struct is well-structured; just avoid cloning it per frame.

- **Performance**:
  - Allocating a `Vec<f32>` on every mouse move isn’t catastrophic (ratios are tiny) but is needless; the zero-allocation pattern is easy and keeps drag latency consistently low.

- **Robustness**:
  - Using early returns instead of “guess” ratios when indices are out-of-range makes drag behavior more predictable if state ever drifts.
  - Adding debug invariants for the layout tree catches subtle corruption early in development.

---

4) Risks and guardrails

- Changing the min-size logic can subtly alter UX: panes may become slightly smaller than `MIN_PANE_SIZE_PIXELS` in extreme nested layouts if you choose the “fallback to 0.0” approach. If this matters, choose “freeze drag when constraints can’t be satisfied” instead.
- Refactoring traversal helpers must carefully preserve the current traversal order; use tests or logging to validate a few example trees (simple 2-pane, 3-pane, nested left/right/vertical combinations).
- Be cautious about cancelling drags when indices are out-of-sync; early-returning from `update_splitter_drag` is safe, but you should rely on `CancelSplitterDrag` or `EndSplitterDrag` to clear state as you already do.

---
