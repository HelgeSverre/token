### 1. Which approach is best for greppable, consistent debug tracing?

**Option A (Debug)** is best given your context:

- **Greppable**:

  - And this function is gated by `#[cfg(debug_assertions)]`, so release logs aren’t affected.

The only time the arguments become harmful is if:

- You start adding **very large payloads** into message variants (e.g., whole document snapshots, big strings), or
- You need **machine-consumable logs** with a strict, argument-free identifier field.

Neither appears to be the case now.

5) Other Rust patterns worth considering?

You’re not missing any “silver bullet,” but there are a couple of variants of the same idea:

1. **Custom `Display` implementations (no extra crates)**
   Example:

   ```rust
   use std::fmt;

   impl fmt::Display for EditorMsg {
       fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
           match self {
               EditorMsg::MoveCursor(dir) =>
                   write!(f, "MoveCursor({:?})", dir),
               EditorMsg::MoveCursorLineStart =>
                   write!(f, "MoveCursorLineStart"),
               // ... and so on for all variants
           }
       }
   }
   ```

   Then `msg_type_name` becomes:

   ```rust
   fn msg_type_name(msg: &Msg) -> String {
       match msg {
           Msg::Editor(m) => format!("Editor::{m}"),
           Msg::Document(m) => format!("Document::{m}"),
           // ...
       }
   }
   ```

   This is essentially **Option C**, but wired through `Display` instead of a one-off function. It has the same maintenance cost and is only worth it if you want **complete control** over formatting or want to reuse that formatting elsewhere.

2. **Separate “kind” and “detail” fields in tracing**
   If you ever want fully structured logs:

   ```rust
   let (kind, detail) = match &msg {
       Msg::Editor(m) => ("Editor", format!("{:?}", m)),
       // ...
   };

   let _span = span!(Level::DEBUG, "update", kind, detail = %detail).entered();
   debug!(target: "message", kind, detail = %detail, "processing");
   ```

   This can help in advanced setups (e.g., log aggregation, filtering on fields), but for local RUST_LOG + ripgrep it’s not necessary.

Given your constraints and YAGNI, these are **nice-to-have** patterns, not must-haves.

6) Compile-time / runtime cost trade-offs

Given `#[cfg(debug_assertions)]` on `msg_type_name` and `update_traced`, the costs are only relevant in debug builds.

**Option A (Debug):**

- **Compile-time**:
  - `#[derive(Debug)]` is already present; no extra macros or derives.
  - No additional compile-time impact.
- **Runtime**:
  - `format!("Editor::{:?}", m)`:
    - Allocates a small `String`.
    - Walks the enum to render it; complexity proportional to number/size of fields in a *single* variant.
  - Overhead is trivial compared to I/O of emitting logs and cloning `Msg` (which you already do).

**Option B (strum::AsRefStr):**

- **Compile-time**:
  - Adds `strum` and `strum_macros` derives on 4–5 enums.
  - Macro expansion and codegen add some compile time, but still small; only matters for very tight compile-time budgets.
- **Runtime**:
  - `m.as_ref()` is just a static string lookup.
  - `format!("Editor::{}", m.as_ref())` is similar cost to Option A’s `format!`, but avoids formatting arguments (since there are none).
  - The performance difference vs Option A is negligible in practice; logging and update logic dominate.

**Option C (manual match):**

- **Compile-time**:
  - 85+ match arms to compile and type-check.
  - More boilerplate means more maintenance overhead, not really compile-time pain.
- **Runtime**:
  - `match` on an enum to a `&'static str` and a `format!` – again trivial.
  - A match of this size might be compiled to a jump table or chain; still much cheaper than logging itself.

Net: **All three have negligible runtime impact for a debug-only tracing system**. The real trade-off is **maintainability vs control**, not performance.

---

7) When to consider the “advanced” path?

Consider moving away from simple Debug formatting (Option A) if:

- You start exporting logs to an external system (e.g., ELK, Datadog) and need a **stable, schema-like field** for the message kind (e.g. `msg_kind = "Editor::MoveCursor"`).
- Message variants begin to carry **large or sensitive payloads**, and you must ensure they’re **never** formatted in logs by default.
- You want to drive tooling (e.g., an in-app debug UI) from a strict set of identifiers with **zero coupling to Debug formatting**.

At that point, you’d revisit:

- **Option B**: `strum::AsRefStr` or similar, to get stable variant names as `&'static str`.
- Or a **custom trait** / `Display` impl giving you:
  - `fn kind(&self) -> &'static str` (e.g., `"Editor::MoveCursor"`)
  - `fn detail(&self) -> String` for arguments, if you still want them.
