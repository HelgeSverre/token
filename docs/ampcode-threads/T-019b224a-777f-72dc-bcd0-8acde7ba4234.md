    pub fn damage(&self) -> Damage {

            Cmd::Redraw => Damage::Full,
            Cmd::RedrawAreas(areas) => Damage::Areas(areas.clone()),

### 2.5 Emit damage from update functions

You don’t need to touch the `View` module to start benefiting; just change update paths where you currently return `Cmd::Redraw`:

  ```rust

  // New (partial):

- **Status text changes only** (e.g. toggling “Saving…”, showing a small message):

  ```rust
  Cmd::RedrawAreas(vec![DamageArea::StatusBar])
  ```

  If the state change *also* affects editor UI (e.g., dirty markers on tabs), use both:

  ```rust
  Cmd::RedrawAreas(vec![DamageArea::EditorArea, DamageArea::StatusBar])
  ```

- **Modal open/close, theme changes, window resize, layout changes (split, close group, etc.)**: keep using `Cmd::Redraw` or let the window-resize path explicitly call `render(..., &Damage::Full)`; these are global changes.

- **Cursor blink**:
  - If no modal: `Cmd::RedrawAreas(vec![DamageArea::EditorArea])`.
  - If modal open: just use `Cmd::Redraw` – as above, modals force full redraw anyway.

This keeps damage tracking out of the `AppModel` and localized to `Cmd` return values, consistent with the Elm-style “view as a pure function of model” idea.

---

3) Rationale and trade-offs

- **Granularity**: Top-level region granularity (editor area + status bar) is enough to avoid redrawing the entire window on every cursor blink or small change, without requiring per-line or per-widget precision.
- **Cmd-based tracking**: Using `Cmd` to carry damage hints keeps the model pure and avoids wiring damage state throughout your data types; the runtime already knows how to examine `Cmd`s to decide whether to render.
- **Renderer unchanged structurally**: You keep the same `render_editor_area`, `render_status_bar`, `render_modals`, and `Frame` API; only the top-level `render` orchestration is aware of damage.
- **Modals & overlays**: Treating them as “force full redraw” avoids all the complexity of overlapping invalidation (especially the `dim()` behavior, which is not easily invertible).

You get a clear, incremental win (partial redraw for the common “no modal, no overlay” path) without complicating the rest of the architecture.

---

4) Risks and guardrails

- **Assuming old pixels are valid**: Partial redraw relies on the buffer containing the previous frame’s contents.
  Guardrail: On any event that could make *all* previous pixels stale (resize, theme change, DPI scale change, toggling modals/overlays), always use `Damage::Full` via `Cmd::Redraw`.

- **Forgetting to request enough damage**: A bug where an update changes something visible but only requests `StatusBar` damage when it also affects tabs, etc., will leave stale pixels.
  Guardrail:
  - Start conservative: favor `EditorArea` + `StatusBar` (or `Full`) until you profile.
  - In debug builds you can optionally assert that some known large changes (like theme switch) always request `Full`.

- **Modals and `dim()`**: The `Frame::dim` function multiplicatively darkens the current pixels. Re-applying it on already dimmed pixels will over-darken the background.
  Guardrail: Always render modals in the `Damage::Full` path only; don’t call `dim()` in partial mode.

---

5) When to consider the advanced path

Consider a more complex damage system (per-group or per-line) only if:

- Profiling shows that redrawing the entire editor area is a noticeable bottleneck for large windows or high-DPI displays, *and* most frames only touch a single group or a few lines.
- You want smooth scrolling with very high frame rates on large files, and CPU usage from re-rendering all groups is significant.
- You introduce more stacked/overlapping widgets (e.g., popups, tooltips) that don’t justify full redraw but change frequently.

---

6) Optional advanced path (brief outline)

If/when needed, you can refine within this design:

- **Per-group damage**: Extend `DamageArea` with `EditorGroup(GroupId)` and teach the renderer to:
  - Clear only `group.rect` for those groups.
  - Call `render_editor_group` just for them.
  - Still draw splitters once when any group is dirty.

- **Line-level damage**: For heavy text editing:
  - Track dirty line ranges in the model (not pixel rects), then map them to pixel rects in the renderer based on `line_height` and scroll offset.
  - Use `fill_rect_px` + a “render visible lines in [y0, y1)” hook.

- **Modal optimizations**: Instead of `dim()` on the full frame:
  - Render background into an off-screen buffer.
  - Copy background region + modal into the on-screen buffer with `blend_rect`/`fill_rect_px`.
  - Then modal changes could be partial-damaged without forcing full redraw.

All of these build on the same core idea: `Cmd` expresses *where* something changed in logical terms; `Renderer::render(model, damage)` translates that into actual drawing operations on `Frame`. The proposed simple path is a good, low-risk first step that should already cut unnecessary redraw work substantially.
