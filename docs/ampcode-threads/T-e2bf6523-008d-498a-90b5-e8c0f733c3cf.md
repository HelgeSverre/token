```rust
pub fn move_all_cursors_left(&mut self, doc: &Document) {
    let len = self.cursors.len();
    for i in 0..len {
        if self.selections[i].is_empty() {
            // No selection: normal one-char move
            self.move_cursor_left_at(doc, i);
        } else {
            // Selection exists: jump to selection start, clear selection
            let start = self.selections[i].start();
            let cursor = &mut self.cursors[i];
            cursor.line = start.line;
            cursor.column = start.column;
            cursor.desired_column = None;

            self.selections[i].collapse_to_start(); // anchor=head=start
        }
    }
    self.deduplicate_cursors();
}

pub fn move_all_cursors_right(&mut self, doc: &Document) {
    let len = self.cursors.len();
    for i in 0..len {
        if self.selections[i].is_empty() {
            self.move_cursor_right_at(doc, i);
        } else {
            let end = self.selections[i].end();
            let cursor = &mut self.cursors[i];
            cursor.line = end.line;
            cursor.column = end.column;
            cursor.desired_column = None;

            self.selections[i].collapse_to_end();
        }
    }
    self.deduplicate_cursors();
}

- For cursors with selection: we already collapsed to the boundary, so the later call is a no‑op.
- For cursors without selection: it still maintains the “selection head == cursor position” invariant.

This matches VSCode/Sublime behavior for both single and multiple cursors:

- Non‑empty selection → jump to edge, clear selection.
- Empty selection → move by one character.

Observations:

- You already do the important parts correctly:
  - Process indices in **reverse document order** (`cursors_in_reverse_order`) so edits at later positions don’t disturb earlier ones.
  - For each selection:
    - Compute `start_offset`/`end_offset` from the current document.
    - Insert the selected text at `end_offset`.
    - Set the cursor to the end of the duplicated text.
    - Clear the selection by creating a new empty `Selection` at the new cursor position.

- That already implements the desired semantics: “insert a copy after each selection and move each cursor to the end of its duplicated text”.

Where it’s fragile / buggy:

1. `line_adjustments` is computed but never used. That’s a clear smell and likely the source of misaligned cursors in more complex cases (multi‑line selections, mix of selection and non‑selection cursors).
2. There’s no post‑operation normalization of cursor/selection state (e.g., no `deduplicate_cursors()` / `merge_overlapping_selections()`), so overlapping/matching positions after duplicate can leave the editor in a slightly inconsistent multi‑cursor state.
3. The multi‑cursor duplicate logic is hand‑rolled here instead of reusing a common “multi‑cursor edit” helper (which you use for other operations), making it easy to get edge cases wrong.

**Recommended minimal fix strategy:**

Keep the high‑level structure (reverse‑order, per‑cursor duplication) but make state updates explicit and remove dead code. I’d do:

1. **Drop the unused `line_adjustments`** entirely for now.

   It’s not applied anywhere, so it’s not currently helping to keep anything in sync. Removing it reduces confusion.

2. **Call a cursor/selection normalization helper after the multi‑cursor block:**

   After:

   ```rust
   let cursors_after: Vec<Cursor> = model.editor().cursors.clone();
   model.document_mut().push_edit(EditOperation::Batch { ... });
   ```

   Add:

   ```rust
   {
       let editor = model.editor_mut();
       editor.deduplicate_cursors();
       editor.merge_overlapping_selections();
       // merge_overlapping_selections will also keep cursor/head invariants
   }
   ```

   This ensures that if multiple duplicate operations land multiple cursors at the same location or produce touching/overlapping selections (possible with weird multi‑line cases), you end up in a sane, VSCode‑like state.

3. **Keep the per‑cursor selection collapse behavior exactly like the single‑cursor path.**

   You already do:

   ```rust
   let new_pos = Position::new(new_line, new_col);
   model.editor_mut().selections[idx] = Selection::new(new_pos);
   ```

   That is equivalent to “cursor at end of duplicated text, selection cleared” and matches the single cursor branch which does:

   ```rust
   let new_offset = end_offset + selected_text.chars().count();
   model.set_cursor_from_position(new_offset);
   model.editor_mut().clear_selection();
   ```

   So no change needed here; just keep it and rely on the normalization step to clean up any cross‑cursor weirdness.

4. **(Optional but nice) factor out duplicate logic to reuse between single and multi cursor paths.**

   To reduce the risk of divergence:

   - Extract a pure helper that, given a `Document` and a single `Cursor+Selection`, returns:
     - The text to insert
     - Insertion position
     - New cursor position
   - Use that helper both in the multi‑cursor loop and in the single‑cursor path.
   - The multi‑cursor branch can then:
     - Iterate indices in reverse
     - Build a vector of `EditOperation::Insert`s from that helper
     - Apply them, update each cursor/selection as you already do
     - Normalize cursor state.

   This keeps semantics identical and focused in one place.

---

3) Rationale and trade‑offs

- Bug 1 fix keeps the change **local** to `move_all_cursors_left/right` and doesn’t touch the higher‑level update flow (`update_editor`). It leverages existing `Selection::start/end` and `collapse_to_*` helpers and naturally extends your all‑cursors movement API to be selection‑aware.
- For Bug 2, the multi‑cursor duplicate implementation is already structured sensibly (reverse order, per‑cursor updates). Rather than redesigning it, the highest‑leverage improvement is to:
  - Remove the misleading unused adjustment logic.
  - Normalize cursor/selection state after the batch.
- A deeper “offset‑based” rework is possible, but you don’t need it unless you’ve actually observed broken content or cursor positions in more pathological multi‑cursor scenarios.

---

4) Risks and guardrails

Bug 1:

- Risk: accidentally changing Shift+Arrow behavior. Guard: do not touch `move_all_cursors_*_with_selection` or `EditorMsg::MoveCursorWithSelection`; only modify the plain `move_all_cursors_left/right`.
- Risk: off‑by‑one or wrong boundary with reversed selections. Guard: rely on `Selection::start()` / `end()` which already canonicalize correctly, and add focused tests:
  - Forward selection then Left/Right with 1 and multiple cursors.
  - Reversed selection then Left/Right with 1 and multiple cursors.

Bug 2:

- Risk: subtle regressions in multi‑cursor duplicate undo/redo. Guard:
  - Keep the `EditOperation::Batch` structure as is; do not change how you record operations.
  - Add tests that exercise undo/redo for multi‑cursor duplicates with:
    - Multiple single‑line selections
    - Mixed selection/no‑selection cursors
    - Multi‑line selections.
- Risk: overlapping selections produce surprising results. Guard:
  - Call `merge_overlapping_selections()` before or after Duplicate, and add a test where two cursors select overlapping ranges and Cmd+D gives a single sensible duplicate.

---

5) When to consider the advanced path

Revisit the design if you see any of the following:

- Complex overlapping/multi‑line multi‑cursor selections still give wrong content or cursor positions after duplicate.
- Undo/redo with multi‑cursor duplicate behaves inconsistently compared to single‑cursor duplicate.
- You want exact VSCode semantics for “duplicate selection” across *all* edge cases, including overlapping cursors, empty selections mixed with non‑empty ones, etc.

---

6) Optional advanced path (if you decide to refactor Bug 2 more deeply)

If you do hit edge‑case problems, a more robust design is:

1. Before any modification, compute and store, for each cursor/selection:
   - Start and end offsets of the selection (or line range if no selection).
2. For multi‑cursor duplicate:
   - Build a list of pure “insert operations” from those offsets.
   - Sort those operations by insertion offset descending.
   - Apply them to the buffer (like you already do for Paste) while also computing the new cursor offset for each operation (end offset + inserted length).
3. After all inserts are applied:
   - Rebuild `editor.cursors` and `editor.selections` from those new offsets (convert via `offset_to_cursor`) instead of mutating them inside the loop.
   - Normalize (`deduplicate_cursors`, `merge_overlapping_selections`).

That approach makes multi‑cursor Duplicate behave like a generic “multi‑insert” operation that’s easy to reason about and test.

But under your current requirements, the simpler fixes above should be “good enough” and low‑risk.

fn word_start_before(buffer: &ropey::Rope, offset: usize) -> usize {
    if offset == 0 {
        return 0;
    }

    // Walk left from offset, first skipping any whitespace,
    // then skipping non-whitespace until we hit another whitespace or BOF.
    let mut i = offset;

    // Skip whitespace left of cursor
    while i > 0 {
        let ch = buffer
            .slice(i - 1..i)
            .chars()
            .next()
            .unwrap_or(' ');
        if ch.is_whitespace() {
            i -= 1;
        } else {
            break;
        }
    }

    // Now skip the word characters
    while i > 0 {
        let ch = buffer
            .slice(i - 1..i)
            .chars()
            .next()
            .unwrap_or(' ');
        if !ch.is_whitespace() {
            i -= 1;
        } else {
            break;
        }
    }

    i
}

fn map_cursor_after_delete_line(
    c: &Cursor,
    total_lines_before: usize,
    deleted_lines: &[usize],
    total_lines_after: usize,
    model: &AppModel,
) -> Cursor {
    use std::collections::HashSet;
    let deleted: HashSet<usize> = deleted_lines.iter().copied().collect();

    // 1. If its line wasn't deleted, just shift it up by the number of deleted lines above.
    if !deleted.contains(&c.line) {
        let deleted_above = deleted_lines.iter().filter(|&&l| l < c.line).count();
        let new_line = c.line.saturating_sub(deleted_above);
        let line_len = model.document().line_length(new_line);
        let new_col = c.column.min(line_len);
        return Cursor::at(new_line, new_col);
    }

    // 2. Its line was deleted: mimic single-cursor DeleteLine behavior.
    // Does there exist a remaining line after this line?
    let mut candidate = c.line + 1;
    while candidate < total_lines_before && deleted.contains(&candidate) {
        candidate += 1;
    }

    let target_orig_line = if candidate < total_lines_before {
        // Move to the first non-deleted line below
        candidate
    } else {
        // No lines below: move to the closest non-deleted line above
        let mut up = c.line;
        while up > 0 {
            up -= 1;
            if !deleted.contains(&up) {
                break;
            }
        }
        up
    };

    // Now map that original target line to its new index in the shrunk document.
    let deleted_before_target = deleted_lines
        .iter()
        .filter(|&&l| l < target_orig_line)
        .count();
    let new_line = target_orig_line.saturating_sub(deleted_before_target);

    let line_len = if total_lines_after > 0 {
        model.document().line_length(new_line)
    } else {
        0
    };
    let new_col = c.column.min(line_len);

    Cursor::at(new_line, new_col)
}

    model.editor_mut().selections = new_selections;
    model.editor_mut().active_cursor_index = 0;

    model.document_mut().push_edit(EditOperation::Batch {
        operations,
        cursors_before,
        cursors_after,
    });

    // ...
}

This preserves:

- Same number of cursors before and after a non‑contiguous delete.
- Per‑cursor behavior roughly matching what a single‑cursor `DeleteLine` would do at that line, with proper line‑index shifts applied.

The example you gave (3 cursors on 3 separated lines with blank lines between):

- `covered_lines` would contain only those 3 lines.
- `is_contiguous` is `false`.
- Each cursor’s line is deleted; each is remapped (usually to the line that slid up into its position, or the nearest surviving line) and you keep 3 distinct cursors.

---

3) Rationale and trade-offs

- Reusing the multi‑cursor patterns from `InsertChar`, `InsertNewline`, and `DeleteBackward` keeps the new `DeleteWordBackward` consistent and minimizes risk.
- The `is_contiguous` flag lets you keep existing “delete a whole block” semantics (collapse to a single cursor) while fixing the clearly wrong behavior for non‑adjacent lines.
- Doing cursor remapping based on original line indices and the deleted set is simpler and less error‑prone than reworking the entire `DeleteLine` algorithm or simulating single‑cursor deletes for each cursor.

Alternatives (not recommended now):

- Rewriting all line‑based multi‑cursor operations to operate per cursor rather than via `lines_covered_by_all_cursors`, then deduping overlapping deletes. This is more invasive and easier to get subtly wrong.
- Trying to perfectly mirror another editor’s exact delete‑word semantics in all Unicode/emoji edge cases; that’s overkill for the current needs.

---

4) Risks and guardrails

- **Edge cases**: deleting words at the very beginning of the document, or when the cursor is immediately after whitespace only. Guard by returning early when `offset == 0` or when calculated `start_offset == end_offset`.
- **Unicode graphemes**: the `word_start_before` helper works on Rust `char`s, not grapheme clusters. That’s consistent with other buffer operations in this code, but if you add emoji/combining support elsewhere, this may need to be revisited.
- **Empty document after DeleteLine**: ensure your “doc empty” branch always normalizes cursors to `(0,0)` and leaves one empty line (or whatever invariant you already use).
- **Performance**: `map_cursor_after_delete_line` uses a `HashSet` and small loops; for typical file sizes the cost is negligible, but you can prebuild the set once per operation and reuse it across cursors (as in the sketch).
- **Undo symmetry**: make sure `cursors_after` passed into `EditOperation::Batch` matches the actual cursor state; otherwise undo/redo will leave cursors in confusing positions.

---

5) When to consider the advanced path

Revisit and consider a more complex design if:

- You start adding more line‑based multi‑cursor operations (e.g. move line up/down, join lines, etc.) and find yourself duplicating line‑mapping logic.
- Users report confusing behavior in more complex selection patterns (multi‑line selections combined with multiple cursors, block selections, etc.).
- You need precise parity with a reference editor’s multi‑cursor semantics (VS Code, Sublime, etc.), especially around word boundaries and line deletion.

---

6) Optional advanced path (outline only)

If/when you want a more robust foundation:

- Extract shared helpers for:
  - “Compute set of deleted lines and per‑cursor target line after deletion” (for any line‑based multi‑cursor op).
  - “Compute word span around/before/after a cursor” (used by both move‑by‑word and delete‑by‑word).
- Represent line‑based operations as a small internal struct:

  ```rust
  struct LineDeletePlan {
      deleted_lines: Vec<usize>,
      cursor_mappings: Vec<(Cursor, Cursor)>, // before → after
  }
  ```

  and have both `DeleteLine` and similar commands build and execute such a plan once, then share its logic for remapping cursors and building `EditOperation::Batch`.

This would centralize the tricky index arithmetic and make future multi‑cursor features easier to implement consistently, but it’s not necessary to fix the two issues you raised.
