I found and fixed a bug where arrow keys with selection were not calling ensure_cursor_visible() after clearing selection and jumping cursor to selection start/end. I added the call to both ArrowLeft and ArrowRight handlers in main.rs.

However, there's a related issue: the viewport adjustment logic doesn't account for scroll direction. If the viewport has been scrolled away from the cursor (e.g., using mouse wheel), pressing an arrow key in the "wrong" direction may not trigger viewport adjustment because the logic only checks boundaries in one direction.

Example scenarios that may be broken:
- Cursor at line 50, scroll viewport down to show lines 100-120, press Up arrow - cursor moves to 49 but viewport may not snap back because it only checks the down boundary
- Cursor near end of document, scroll viewport far up, press Up arrow - similar issue

The reference doc docs/EDITOR_UI_REFERENCE.md has relevant sections:
- Section 5.1 "Scroll Margins / Keep-in-View Zone" - describes scroll padding/margins
- Section 5.5 "Scroll Reveal Strategies" - describes different strategies for revealing cursor (minimal vs centered vs top-aligned)

The ensure_cursor_visible() function in src/model/editor.rs needs to check BOTH boundaries (top and bottom) regardless of movement direction. Currently it may be broken

    pub fn ensure_cursor_visible_with_mode(
        &mut self,
        document: &Document,
        mode: ScrollRevealMode,
    ) {
        let cursor = &self.cursors[0];
        let padding = self.scroll_padding;
        let total_lines = document.line_count();

        // --- Vertical scrolling ---

            let max_top = total_lines.saturating_sub(self.viewport.visible_lines);

            let off_below = line > safe_bottom;

3) How this maps to your questions

**1. Should we add a `ScrollRevealMode` enum with variants like `Minimal`, `TopAligned`, `BottomAligned`, `Centered`?**

Yes; but keep it as an **internal geometry primitive**, not something most code touches.

- It matches how other editors model this (see §4).
- It keeps the scroll math centralized and testable.
- It gives you room to later implement “center on search result/go-to-line” without reinventing the wheel.

**2. Should `ensure_cursor_visible()` take an optional movement direction hint?**

Not directly. For API cleanliness:

- Keep `ensure_cursor_visible(&mut self, doc)` as the simple, default “minimal” reveal that most callers continue to use.
- Add `ensure_cursor_visible_with_mode(&mut self, doc, mode)` as the flexible underlying primitive.
- Add a **separate** convenience method (on `AppModel` or `EditorState`) that accepts a high-level hint (`Direction` or `VerticalRevealHint`) and maps it to a `ScrollRevealMode`.

This avoids breaking existing call sites and keeps `editor.rs` decoupled from UI‑level concepts like `EditorMsg`.

**3. How do other editors (VS Code, JetBrains) handle this?**

Conceptually, you’d be aligning with their patterns:

- **JetBrains / IntelliJ Platform**
  - Has `ScrollType` enum: e.g. `MAKE_VISIBLE` (minimal), `CENTER`, `CENTER_UP`, `CENTER_DOWN`, `REVEAL`, etc.
  - Caret-moving actions call `scrollToCaret(ScrollType.MAKE_VISIBLE)` or a more specific type depending on intent.
  - PageUp/PageDown and “jump” actions often use a more aggressive reveal (center/up/down) while basic typing uses minimal.
  - Your `ScrollRevealMode` is essentially a Rust-ified version of this.

- **VS Code**
  - Uses different “reveal” functions: `revealRange`, `revealRangeInCenter`, `revealRangeInCenterIfOutsideViewport`.
  - Caret motion and typing mostly use a minimal “make visible” behavior with scroll margins.
  - Navigation commands (go to definition, search result, etc.) use center-oriented reveals.
  - Again, this maps nicely to `Minimal` vs `Centered` / `TopAligned` / `BottomAligned` strategies.

So yes, you’re following a well-established pattern rather than inventing an exotic behavior.

**4. What’s the cleanest API design that doesn’t require changing every call site?**

The pattern above:

- `EditorState::ensure_cursor_visible(document)`
  → legacy API, always `Minimal`; all existing code can stay as-is.

- `EditorState::ensure_cursor_visible_with_mode(document, ScrollRevealMode)`
  → advanced primitive, used by a small number of higher-level helpers.

- `AppModel::ensure_cursor_visible_with_vertical_hint(dir: Option<Direction>)`
  → ergonomic facade for `update.rs`, mapping arrow/Page keys to `TopAligned` / `BottomAligned` only when needed.

You only touch:

- `update_editor` cases for `MoveCursor(Up/Down)`, `MoveCursorWithSelection(Up/Down)` if desired, and `PageUp`/`PageDown`.

Everything else remains unchanged.

4) Rationale and trade-offs

- **Centralized logic**: All scroll math remains in `EditorState`, following the geometry model in `EDITOR_UI_REFERENCE.md`.
- **Minimal surface change**: One new enum, one new method, plus a thin helper — no breaking changes.
- **Good UX**: Direction-aware reveal only kicks in when the cursor is *outside* the safe zone, so normal step-wise movement is unaffected.
- **Future-proof**: `Centered` is ready for search/go-to-line/diagnostic jumps without more refactors.

Alternative (not recommended now): Put all direction logic into `update.rs` by duplicating safe-zone math and conditionally tweaking `viewport.top_line`. That avoids changing `editor.rs` but scatters scroll geometry knowledge and makes it harder to keep consistent.

---

5) Risks and guardrails

- **Off-by-one and tiny viewports**: Verify behavior when:
  - `visible_lines <= 2 * scroll_padding + 1`
  - document shorter than viewport
  - cursor at very first or very last line
- **Interaction with existing PageUp/PageDown math**:
  Your current PageUp/PageDown already mutate `viewport.top_line`; the new reveal should mostly be a no-op when cursor and viewport move together. If you see surprising jumps, you can gradually simplify PageUp/PageDown to rely more on `ScrollRevealMode` and less on hand-rolled `top_line` tweaks.
- **Multi-cursor**: For now, behavior is defined by the primary cursor only (as today). If you later add “reveal all cursors” semantics, this API still works; you’d just adjust the implementation to consider multiple lines.

Guardrail: Add a few unit/integration tests that assert:

- Cursor off-screen above, press Down → appears at bottom of safe zone.
- Cursor off-screen below, press Up → appears at top of safe zone.
- Cursor inside safe zone, press Up/Down → viewport does not jump, only minimal scroll when crossing margins.

---

6) When to consider the advanced path

You might revisit and complicate this design if:

- You introduce a proper `ScrollMode` state machine (`CURSOR_LOCKED`, `FREE_BROWSE`, `REVEAL_PENDING`) as sketched in the reference.
- You add more distinct reveal behaviors (e.g., “keep caret relative position on PageUp/PageDown” vs absolute align).
- You support soft-wrapped lines with pixel-level scrolling (then reveal modes might need pixel-based variants).

In that world, `ScrollRevealMode` and `ScrollMode` would likely interact (e.g. “center if outside + cursor-locked”), but today’s enum design is a solid foundation.

---

7) Optional advanced path (brief)

If/when you want richer behavior:

- Add `ScrollMode` to `EditorState` as in the reference (`CURSOR_LOCKED`, `FREE_BROWSE`, `REVEAL_PENDING`).
- Mouse wheel/scrollbar drag set `FREE_BROWSE` and do **not** auto-reveal the cursor.
- Next edit or cursor key sets `REVEAL_PENDING` and calls `ensure_cursor_visible_with_mode` with a chosen `ScrollRevealMode` (e.g. `Centered` for “jump to definition”).
- After reveal, switch back to `CURSOR_LOCKED`.

This gives you a very VS Code / JetBrains-like scroll model. But for now, the enum + mode-aware `ensure_cursor_visible` is the simplest, high-leverage upgrade that solves your direction-aware reveal issue.
