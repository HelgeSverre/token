3) Why render vs hit-test can mismatch (the real bug)
------------------------------------------------------

The important detail: **coordinate systems and DPI scaling.**

- `metrics.file_tree_row_height` is a **scaled** (physical pixel) value:

  ```rust
  // src/model/mod.rs
  impl ScaledMetrics {
      const BASE_FILE_TREE_ROW_HEIGHT: f64 = 22.0;

      pub fn new(scale_factor: f64) -> Self {
          Self {
              // ...
              file_tree_row_height:
                  (Self::BASE_FILE_TREE_ROW_HEIGHT * scale_factor).round() as usize,
              // ...
          }
      }
  }
  ```

- The renderer uses:
  - `Frame` sized from `window.inner_size()` (physical size).
  - `row_height = metrics.file_tree_row_height` as **physical pixels** when rendering.
- Winit’s `WindowEvent::MouseInput` positions `x` and `y` are in **logical coordinates** (device-independent pixels).
- But the sidebar hit-test code:
  - Uses **physical** values for `sidebar_width` and `row_height`:

    ```rust
    let sidebar_width = workspace.sidebar_width(self.model.metrics.scale_factor) as f64;
    // sidebar_width_logical * scale_factor  => physical

    let row_height = self.model.metrics.file_tree_row_height as f64; // physical
    ```

  - Compares them directly to **logical** mouse coordinates `x` and `y`.

So the mismatch is:

- Rendering is done in **physical pixels** (scaled by `scale_factor`).
- Hit testing divides **logical y** by a **physical row_height**:

  ```rust
  let clicked_row = (y /* logical */ / row_height /* physical */) as usize;
  ```

- And compares **logical x** with **physical sidebar_width**:

  ```rust
  if x /* logical */ < sidebar_width /* physical */ { ... }
  ```

When `scale_factor != 1.0`, this leads to:

- The visual row boundaries on screen do not line up with the `clicked_row` indices.
- For a common case like `scale_factor = 2.0`:
  - `row_height` used for rendering might be ~44 physical px.
  - Mouse `y` comes in as ~22 logical px for that same visual height.
  - `clicked_row = 22 / 44 = 0` → still row 0 while the cursor may visually be in row 1.
- The net effect is that clicks are biased toward the wrong row, typically off by about **one item up or down**, exactly as you described.

This is a **unit mismatch (logical vs physical)**, not an internal off-by-one in the sidebar rendering loop itself.

Note: `visible_index` and `workspace.scroll_offset`

- `render_sidebar` tracks a `visible_index`, and `Workspace` has a `scroll_offset` field, but:
  - `scroll_offset` isn’t used in rendering or hit testing yet.
  - `visible_index` is incremented but never consulted.
- So **scrolling isn’t implemented** yet; the tree always starts at the first item at `y = 0`. That’s not the cause of the current off-by-one bug, but it’s a future concern if you add scrolling.

Summary answers
---------------

1. **Where rendered / first-item y-offset:**
   - Sidebar is rendered in `Renderer::render_sidebar` (`src/view/mod.rs`).
   - Background and first row start at `y = 0` of the sidebar area.
   - First item’s rectangle is `[0, row_height)`, with text baseline at `y = row_height - 4`.

2. **Where hit testing / row calculation:**
   - Hit testing is in `App::window_event` for `MouseInput::Pressed(Left)` (`src/runtime/app.rs`).
   - It checks `x < sidebar_width(...)` and then computes `clicked_row = (y / metrics.file_tree_row_height as f64) as usize`, then uses `FileTree::get_visible_item(clicked_row, ...)`.

3. **Why mismatch:**
   - `file_tree_row_height` and `sidebar_width` are **scaled** (physical pixels via `ScaledMetrics` and `scale_factor`).
   - Mouse `x, y` from winit are **logical** coordinates.
   - Comparing logical mouse coordinates directly against physical dimensions mixes units, so on HiDPI (scale_factor ≠ 1.0) the hit-tested row index does not match the visually rendered row, leading to the observed off-by-one row selection.

If you fix this by converting either:

- mouse `x, y` → physical (`* model.metrics.scale_factor`), **or**
- all sidebar dimensions used for hit testing → logical (`/ model.metrics.scale_factor`),

then the render and hit-test positions for the sidebar should line up correctly. This is a small change (scope S: <1h) and doesn’t require touching the rendering logic itself.
