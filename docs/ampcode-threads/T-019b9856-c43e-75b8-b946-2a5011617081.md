## Zed Editor Panel System Architecture

Zed's dockable panel system is built around a **trait-based abstraction** that separates panels from the main editor UI. Here's a comprehensive breakdown of how it works:

### Core Trait Architecture

#### [Panel Trait](https://github.com/zed-industries/zed/blob/main/crates/workspace/src/dock.rs#L96-L128)

The foundation is the [`Panel` trait](https://github.com/zed-industries/zed/blob/main/crates/workspace/src/dock.rs#L96-L128) that any dockable UI component must implement:

```rust
pub trait Panel: Focusable + EventEmitter<PanelEvent> + Render + Sized {
    fn persistent_name() -> &'static str;      // Unique identifier for serialization
    fn panel_key() -> &'static str;            // Key for event dispatch
    fn position(&self, window: &Window, cx: &App) -> DockPosition;
    fn position_is_valid(&self, position: DockPosition) -> bool;
    fn set_position(&mut self, position: DockPosition, window: &mut Window, cx: &mut Context<Self>);
    fn size(&self, window: &Window, cx: &App) -> Pixels;
    fn set_size(&mut self, size: Option<Pixels>, window: &mut Window, cx: &mut Context<Self>);
    fn icon(&self, window: &Window, cx: &App) -> Option<ui::IconName>;
    fn icon_tooltip(&self, window: &Window, cx: &App) -> Option<&'static str>;
    fn toggle_action(&self) -> Box<dyn Action>;
    fn icon_label(&self, _window: &Window, _: &App) -> Option<String> { None }
    fn is_zoomed(&self, _window: &Window, _cx: &App) -> bool { false }
    fn starts_open(&self, _window: &Window, _cx: &App) -> bool { false }
    fn set_zoomed(&mut self, _zoomed: bool, _window: &mut Window, _cx: &mut Context<Self>) {}
    fn set_active(&mut self, _active: bool, _window: &mut Window, _cx: &mut Context<Self>) {}
    fn pane(&self) -> Option<Entity<Pane>> { None }
    fn remote_id() -> Option<proto::PanelId> { None }
    fn activation_priority(&self) -> u32;
    fn enabled(&self, _cx: &App) -> bool { true }
}
```

    fn set_size(&self, size: Option<Pixels>, window: &mut Window, cx: &mut App);

### Concrete Implementation Example: ProjectPanel

Here's how [ProjectPanel](https://github.com/zed-industries/zed/blob/main/crates/project_panel/src/project_panel.rs#L6291-L6364) implements the Panel trait:

```rust
impl Panel for ProjectPanel {
    fn position(&self, _: &Window, cx: &App) -> DockPosition {
        match ProjectPanelSettings::get_global(cx).dock {
            DockSide::Left => DockPosition::Left,
            DockSide::Right => DockPosition::Right,
        }
    }

    fn position_is_valid(&self, position: DockPosition) -> bool {
        matches!(position, DockPosition::Left | DockPosition::Right)
    }

    fn set_position(&mut self, position: DockPosition, _: &mut Window, cx: &mut Context<Self>) {
        settings::update_settings_file(self.fs.clone(), cx, move |settings, _| {
            let dock = match position {
                DockPosition::Left | DockPosition::Bottom => DockSide::Left,
                DockPosition::Right => DockSide::Right,
            };
            settings.project_panel.get_or_insert_default().dock = Some(dock);
        });
    }

    fn size(&self, _: &Window, cx: &App) -> Pixels {
        self.width.unwrap_or_else(|| ProjectPanelSettings::get_global(cx).default_width)
    }

    fn set_size(&mut self, size: Option<Pixels>, window: &mut Window, cx: &mut Context<Self>) {
        self.width = size;
        cx.notify();
        cx.defer_in(window, |this, _, cx| {
            this.serialize(cx);
        });
    }

    fn icon(&self, _: &Window, cx: &App) -> Option<IconName> {
        ProjectPanelSettings::get_global(cx).button.then_some(IconName::FileTree)
    }

    fn icon_tooltip(&self, _window: &Window, _cx: &App) -> Option<&'static str> {
        Some("Project Panel")
    }

    fn toggle_action(&self) -> Box<dyn Action> {
        Box::new(ToggleFocus)
    }

    fn persistent_name() -> &'static str {
        "Project Panel"
    }

    fn panel_key() -> &'static str {
        PROJECT_PANEL_KEY  // "ProjectPanel"
    }

    fn activation_priority(&self) -> u32 {
        0  // Lower = higher priority (shows first in status bar)
    }
}

impl Focusable for ProjectPanel {
    fn focus_handle(&self, _cx: &App) -> FocusHandle {
        self.focus_handle.clone()
    }
}

### Panel Position Cycling

Panels support moving between docks via context menu. The default implementation provides automatic cycling:

```rust
fn move_to_next_position(&self, window: &mut Window, cx: &mut App) {
    let current_position = self.position(window, cx);
    let next_position = [
        DockPosition::Left,
        DockPosition::Bottom,
        DockPosition::Right,
    ]
    .into_iter()
    .filter(|position| self.position_is_valid(*position, cx))
    .skip_while(|valid_position| *valid_position != current_position)
    .nth(1)
    .unwrap_or(DockPosition::Left);

    self.set_position(next_position, window, cx);
}
```

### Rendering and Resizing

The Dock renders with a resize handle overlay positioned based on direction:

```rust
impl Render for Dock {
    fn render(&mut self, window: &mut Window, cx: &mut Context<Self>) -> impl IntoElement {
        if let Some(entry) = self.visible_entry() {
            let size = entry.panel.size(window, cx);

            div()
                .flex()
                .map(|this| match self.position().axis() {
                    Axis::Horizontal => this.w(size).h_full().flex_row(),
                    Axis::Vertical => this.h(size).w_full().flex_col(),
                })
                .child(entry.panel.to_any())
                .when(self.resizable(cx), |this| {
                    // Add resize handle (6px, positioned absolutely)
                    this.child(create_resize_handle())
                })
        }
    }
}

### Key Patterns and Design Decisions

1. **Type Erasure**: `PanelHandle` provides a trait object that lets workspace manage heterogeneous panels without generics
2. **Settings-Based Positioning**: Panel positions are stored in settings, persisted across sessions
3. **Activation Priority**: Panels are sorted by priority for deterministic ordering in status bar
4. **Zoom Layer**: When zoomed, panels expand to hide other UI via a modal layer
5. **Subscription-Based Updates**: Position changes trigger subscriptions that re-route panels between docks
6. **Persistence**: Panel state (size, position, visibility) automatically serialized to workspace database
7. **Double-Click Resize**: Double-clicking resize handle resets to default size

- Special routing for CSV: `Msg::Editor` and `Msg::Document` can be intercepted and converted to `CsvMsg`s.

   ```rust
   // messages.rs
   pub enum Msg {
       // existing...
       Panel(PanelMsg),
       Dock(DockMsg),
   }

   ```rust
   Msg::Dock(m)  => dock::update_dock(model, m),
   Msg::Panel(m) => panel::update_panel(model, m),
   ```

   So it’s clear where panel/dock logic lives.

   The spec defines:

   ```rust
   pub trait Panel: Send + Sync {
       fn update(&mut self, msg: PanelMsg, model: &mut AppModel) -> Cmd;
   }
   ```

   - You will have duplicated state transitions:

   - It also breaks the “all state transformations flow through update functions” principle documented in `update/mod.rs`.

   - Make `Panel::update` operate only on *panel-local state*, not the full `AppModel`, e.g.:

     fn update(
         &mut self,
         msg: PanelMsg,
         app: &mut AppModel, // optional, or a smaller context type

     ```

   ➜ Spec is missing:
   - A clear location/API for “layout computation” for editor area + docks (analogous to `ViewportGeometry`).
   - Provision for passing those rects to both Renderer and event handlers.

2. **Mouse integration / hit testing**

   - Current mouse handling in `app.rs` is full of sidebar-specific logic:

     - Check status bar
     - Check for sidebar resize hit zone (using `workspace.sidebar_width`)
     - Hit-test sidebar rows and chevron areas using file-tree metrics
     - Click in sidebar ⇒ `focus_sidebar()` and `WorkspaceMsg::*`

   - Specced docks introduce:
     - Resize handles for left/right/bottom docks.
     - Tab header click for active panel changes.
     - Panel content clicks (file explorer, etc.).

   None of this hit-testing is specified. This is a **big practical gap**.

   ➜ Spec should add at least:

   - A short section on **mouse routing for docks**:
     - One “dock hit-test” function (similar to `geometry::is_in_status_bar`) that:
       - Given `(x, y)` returns:
         - dock position (if in a dock)
         - whether it’s in header/tab area, resize handle, or content area
     - Define new messages:
       - `DockMsg::StartResize { position: DockPosition, initial_xy: (f32, f32) }`
       - `DockMsg::UpdateResize { position: DockPosition, current_xy: (f32, f32) }`
       - `DockMsg::ClickTab { position: DockPosition, panel_id: PanelId }`
     - State clearly that:
       - Sidebar-specific hit-testing will be removed; file-explorer panel hit-testing should move into panel/dock code (or share code).

3. **Rendering order / overlays vs docks**

   - Current `Renderer::compute_effective_damage` forces full redraw with modal/drop/debug overlays.
   - Spec doesn’t say how modals should be drawn relative to docks, but in practice:
     - Docks are “behind” modals.
     - You can safely treat dock changes as just part of the editor area.

   This is not critical but worth encoding in spec: **docks live in the same layer as editor area**, under modals and overlays.

### 5. Keymap system & command dispatching

**Current state**

- `CommandId` in `commands.rs` lists palette-exposed commands (NewFile, SplitHorizontal, ToggleCsvView, etc.), but nothing for:
  - “Toggle File Explorer”
  - “Toggle Terminal”
  - “Focus/Toggles for specific panels”
  - “Focus next/prev panel in dock”

- `App::dispatch_command()` maps a `keymap::Command` to Vec<`Msg`> via `command.to_msgs()`, then runs `update()` for each.

**Gaps vs spec**

1. **No panel/dock commands registered**

   - Spec has a rich keybinding story for panels but doesn’t mention:
     - New `CommandId` variants.
     - How those map to `DockMsg` or `PanelMsg`.
     - Whether these commands are exposed in the command palette.

   ➜ Add to spec:

   - New command IDs, e.g.:

     ```rust
     enum CommandId {
         // ...
         ToggleFileExplorerPanel,
         ToggleTerminalPanel,
         ToggleBottomPanel,        // if any generic ones
         FocusNextPanelInDock,
         FocusPrevPanelInDock,
     }
     ```

   - And a short mapping:

     ```rust
     CommandId::ToggleFileExplorerPanel => Msg::Dock(DockMsg::FocusOrTogglePanel(PanelId::FILE_EXPLORER))
     ```

   - Default keybindings in `defaults`/keymap YAML.

2. **Key contexts for editor vs dock commands**

   - Some commands should be **globally active** (e.g., toggle explorer from editor or dock).
   - Others should be **dock-only** (panel cycling, panel-local operations).

   Spec should call out:
   - Which new commands use `when: editor_focused || dock_focused`
   - Which use `when: dock_focused` only.

Without this, you risk weird interactions, e.g. `Cmd+]` cycling panels while typing in the editor.

### 6. Model/state architecture concerns

**Current state**

- Sidebar is deeply embedded in `Workspace` and `UiState`:

  - `Workspace`:
    - `sidebar_visible`
    - `sidebar_width(...)`
    - file-tree state (scroll_offset, expanded_folders, etc.)
  - `UiState`:
    - `SidebarResizeState`
    - `FocusTarget::Sidebar`

- App model handles geometry but **does not** consider docks (only tab bar height + status bar).

**Spec vs reality**

1. **State duplication risk: sidebar vs file-explorer panel**

   - Spec suggests migrating file explorer into `panels/file_explorer.rs` and “removing sidebar-specific state from `workspace.rs`”.
   - However:
     - File tree model is conceptually part of the workspace, not the panel per se.
     - Only **visibility, size, focus** are truly view-concerns.

   ➜ Clarify in spec:

   - What stays in `Workspace`:
     - File tree structure.
     - Scroll offset, selection, expanded folders (these are “model”, even if currently co-located with view code).
   - What moves into `DockState` / panel state:
     - Whether the explorer panel exists in a given dock.
     - Which panel is active and focused.
     - Dock sizes.

   And explicitly deprecate:

   - `workspace.sidebar_visible`
   - `WorkspaceMsg::StartSidebarResize`, `UpdateSidebarResize` (or rename them with dock semantics).

2. **`FocusTarget` evolution**

   - `FocusTarget` today has at least `Editor`, `Sidebar`, plus modal-related bits.
   - Spec doesn’t say how this enum will evolve.

   You probably want:

   ```rust
   pub enum FocusTarget {
       Editor,
       Dock(DockPosition), // or Dock(DockPosition, PanelId) if you want per-panel
       Modal(ModalId),
       // ...
   }
   ```

   and remove `Sidebar` entirely, using `Dock(Left)` with `PanelId::FILE_EXPLORER` to represent “file explorer in left dock is focused”.

   This should be spelled out, because it affects:

   - `input::is_sidebar_focused` (which becomes generic)
   - `App::get_key_context()`
   - Any other code that pattern-matches on `FocusTarget::Sidebar`.

3. **Persistence**

   - Spec covers dock layout persistence but doesn’t mention how it interacts with:
     - Existing session data (workspace state, scroll positions, open editors).
     - `EditorConfig` / `config_paths`.

   At minimum, document that:

   - Dock layout is persisted **separately** (e.g., `dock-layout.yaml`) and loaded early in `AppModel::new`.
   - It does **not** duplicate file-tree state; it only stores **which panels** are in which docks, their sizes, and open/closed/focused state.

---

3) Rationale and trade-offs (brief)

- The main architectural pressure point is that the current system has:
  - A simple, global `FocusTarget`.
  - A mostly editor-centric keymap.
  - A single hard-coded sidebar.

- The panel spec is ambitious but omits how to reconcile those three with a more general dock/panel model.
- Adding a small number of new primitives (extended `FocusTarget`, `KeyContext`, `Msg` variants, and a generic panel input layer) lets you implement docks incrementally without rewriting the world.

---

4) Risks and guardrails

- **Risk: desynchronized focus** between `UiState::focus` and `DockLayout::focused_dock`.
  ➜ Guardrail: choose exactly one as source of truth and document how the other is derived (or drop it).

- **Risk: reintroducing side-effectful panel code that mutates `AppModel` ad hoc.**
  ➜ Guardrail: keep the “all state goes through `update()`” rule; panels emit `Msg`s instead of directly editing unrelated parts of the model.

- **Risk: messy mixed input routing** (some keys handled via keymap, others via random `handle_*_key` functions).
  ➜ Guardrail: define the capture order in the spec and consolidate panel input under one generic `handle_panel_key` or fully rely on keymap where possible.

- **Risk: forgotten sidebar-specific code paths** (renderer, resizing, hit-testing) causing bugs after migration.
  ➜ Guardrail: add a “sidebar removal checklist” in the spec (renderer paths, `WorkspaceMsg`s, `SidebarResizeState`, geometry assumptions, key handlers).

---

5) When to consider the advanced path

Move beyond the simple approach when:

- You add 3+ complex panels (e.g., terminal, chat, tasks) that all want non-trivial keyboard/mouse behavior.
- You need per-panel keymaps or plugin panels, which will pressure the current `KeyContext` and Command/Msg design.
- Partial redraw performance for docks becomes a bottleneck (frequent panel updates, animations, etc.).

---

6) Optional advanced path (very brief)

If you hit those thresholds, consider:

- A more explicit **“focus surface”** abstraction:

  ```rust
  enum FocusTarget {
      Editor(EditorId),
      Panel(PanelId),
      Modal(ModalId),
      // ...
  }
  ```

- A generic `InputTarget` trait (`handle_key`, `handle_mouse`) implemented by editor groups and panels, with a small router that sends events based on `FocusTarget`.
- Panel-specific keymaps (each panel can contribute bindings plus its own context keys), merged into the global keymap at startup.

For now, the simpler extensions outlined above are enough; just update the spec to cover these integration points before implementation.

### 5. Command system & how menu actions execute

**Existing command systems**

- `token::keymap::Command`:
  - Produced by keymap lookup.
  - Has `to_msgs()` which returns `Vec<token::messages::Msg>`.
  - `App::dispatch_command` loops over these messages, calling `update(&mut self.model, msg)` and keeping the last `Option<Cmd>` (this already silently drops earlier `Cmd`s, which is a minor pre-existing quirk).
- `token::commands::CommandId`:
  - Used by the command palette (`COMMANDS` static registry).
  - Each entry has `id`, label, and a **static keybinding string** for display.

**Spec’s `MenuAction`**

- `MenuAction::Messages(Vec<crate::messages::Msg>)`.
- Helper: `MenuAction::from_command(cmd: crate::keymap::Command) -> Self` that just wraps `cmd.to_msgs()`.

**Integration challenges**

- **Who executes `MenuAction::Messages`.**
  - Spec says: `update()` handles `ContextMenuMsg::ActivateItem` and “executes the item’s `MenuAction`”.
  - Current `update` signature: `fn update(model: &mut AppModel, msg: Msg) -> Option<Cmd>`.
  - `update` does **not** know about `Keymap`, but it *can* apply `Vec<Msg>`:
    - Loop messages and merge `Cmd`s via `Cmd::Batch` or `Damage::merge`, similar to what `Cmd::Batch` does.

- **Spec’s ownership confusion:**
  - The spec also shows `fn build_context_menu(&self, request: &ContextMenuRequest) -> ContextMenuState` on `App` (to access `self.keymap`).
  - Then adds a note: “If `update()` doesn't have access to `Keymap`, (…) menu building can happen in `App::process_cmd()` instead.”
  - There is **no `App::process_cmd` today**, and `update` doesn’t have keymap access.
  - You need to choose one model:
    1. **Menu built in `App`**:
       - Right-click handler:
         - Hit-test, build `ContextMenuTarget`.
         - Call `build_context_menu(&self, &request)` (uses `self.keymap` for shortcut hints).
         - Directly set `self.model.ui.context_menu = Some(context_menu_state)`.
         - Optionally still send a `Msg::Ui(UiMsg::ContextMenu(ContextMenuMsg::Opened))` if model logic needs to react.
    2. **Menu built in `update`**:
       - Then `Keymap` or `ShortcutHintProvider` must be passed through messages, or `Keymap` must move into `AppModel`, which is a larger refactor.

  - Given your current architecture (keymap owned by `App`, `update` pure over `AppModel`), the **simplest is option 1**: build menus in `App`, not in `update`.

- **Cmd aggregation for menu actions.**
  - When executing `MenuAction::Messages(Vec<Msg>)`, you should:
    - Preserve **all** `Cmd`s from all messages, not just the last non-`None`.
    - Reuse the pattern from `Cmd::Batch` and `Damage::merge`, or create a helper like:

      ```rust
      fn run_msgs(model: &mut AppModel, msgs: Vec<Msg>) -> Option<Cmd> {
          let mut cmds: Vec<Cmd> = Vec::new();
          for msg in msgs {
              if let Some(cmd) = update(model, msg) {
                  cmds.push(cmd);
              }
          }
          match cmds.len() {
              0 => None,
              1 => Some(cmds.pop().unwrap()),
              _ => Some(Cmd::Batch(cmds)),
          }
      }
      ```

  - Spec doesn’t mention this; without it you risk silently losing side effects.

- **Avoid confusion between `CommandId` and `keymap::Command`.**
  - Context menus should use **`keymap::Command`** directly for actions and hints.
  - Do **not** reuse `commands::COMMANDS` static `keybinding` strings (they’re not aware of user customization).

**Current situation**

- Command palette uses `commands::COMMANDS`, which embeds **hardcoded** keybinding strings like `"⌘C"`, `"⇧⌘Z"`.

- **Locate or add a “bindings for command” API.**

    - Find the first binding where conditions are broadly compatible (or ignore conditions for display purposes in V1).

    - Multiple bindings per command.

  - For V1:
    - Display **the first matching simple keystroke** (no chords), and ignore the rest.
    - Document this limitation.

- **KeyContext-dependent bindings.**
  - A command may have different shortcuts depending on context (e.g., editor vs sidebar).
  - ShortcutHintProvider currently doesn’t take a context; spec only passes `Command`.
  - For context menus you probably want **context-agnostic** hints for now; just be aware that:
    - In rare cases, the shown shortcut may not be active in the current region if keymap conditions conflict.
    - This is acceptable for V1 but worth a note in the spec.

- Building menus and shortcut hints **from `App`** (where `Keymap` already lives) avoids invasive changes to `update()` and the `token` library API.

- Adding `context_menu_active` to `KeyContext` gives you future flexibility (e.g., disabling commands when menu is open) while staying backward-compatible if you don’t change the default keymap immediately.
- Reusing geometry helpers centralizes all hit-testing logic and reduces off-by-one bugs in multiple places.

- **Risk: brittle multi-command execution / damage merging.**

- **Risk: ambiguous UX when clicking outside menu.**
