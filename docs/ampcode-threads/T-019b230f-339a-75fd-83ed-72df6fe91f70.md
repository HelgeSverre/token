I implemented syntax highlighting using tree-sitter with an async background parsing architecture. I'm debugging an issue where syntax highlighting doesn't update correctly after document edits.

I added comprehensive debug tooling:
- Enhanced the DebugOverlay (toggle with F8) to show syntax highlighting state, including document revision, highlight statistics, current line tokens, and a timeline of recent syntax events (ParseScheduled, ParseStarted, ParseCompleted, ParseStale, HighlightsCleared, HighlightsApplied)
- Extended the StateDump (F7) to include syntax highlight info in JSON dumps
- Added tracing throughout the syntax pipeline in src/runtime/app.rs and src/update/syntax.rs

The user reported that HighlightsApplied and HighlightsCleared events never appear in the debug overlay. I added extensive tracing to investigate.

Key findings from running with RUST_LOG=debug:
- The syntax parsing IS working - I can see "update_syntax: ParseCompleted received for doc=1 rev=3" and "Applied syntax highlights for document DocumentId(1), revision 3" in the logs
- The code path that records overlay events is being reached
- The overlay events should be recorded but might not be visible because they happen before the overlay is toggled on

The syntax flow is:
1. Edit triggers DebouncedSyntaxParse command
2. After debounce, ParseReady message is sent
3. update_syntax handles ParseReady, returns RunSyntaxParse command
4. Worker thread parses and sends ParseCompleted message
5. update_syntax handles ParseCompleted, stores highlights, records HighlightsApplied event to overlay

- **User-visible effect**

- **Correctness**
  - You already enforce correctness for **new** highlights using revision checks and full reparses.
  - The only remaining issue is that the *displayed* highlights are a snapshot from the previous revision. That’s exactly what every async highlighter does: display last known-good state until new state is ready.
- **Why not clear?**
  - Clearing exists purely to avoid showing stale/misaligned colors — but that creates a strictly worse UX (FOUC) with no real correctness gain.
  - With your incremental-bug fix (always `parse(source, None)`), the previous misalignment issue was caused by wrong tree reuse, not by reusing old highlight buffers in the UI.

1. **Keep old highlights** (this proposal)

   - Stale-but-reasonable colors for a few tens of milliseconds.

2. **Shift highlight line numbers manually**

- Maintain, per document, a `Tree` in the worker.
- Send precise edit deltas (old byte range, new byte length) from UI to worker.

  - Call `tree.edit(&InputEdit)` per change.

- Extract highlights from the new tree as you already do.
- This gives you both performance and much more accurate interim highlights, but it’s a bigger project.
