I've been fixing multi-cursor bugs in a Rust text editor. Key patterns I established:

- Operations that should work on all cursors check has_multiple_cursors() first
- Multi-cursor edits process cursors using cursors_in_reverse_order() which returns cursor indices sorted by document position (highest first)
- Multi-cursor edits wrap in EditOperation::Batch with cursors_before/cursors_after for proper undo
- Delete/modify lines from bottom to top (reverse order) to avoid offset invalidation

Critical pattern I just discovered and fixed:
- When an operation at one cursor changes line numbers (inserting/deleting newlines), ALL OTHER cursors that are below/above that point must be adjusted
- I fixed this for InsertNewline, Paste, Duplicate, and DeleteLine
- The pattern is: after processing each cursor, loop through all other cursors and adjust their line numbers based on lines added/removed

The bug being reported now is for DeleteBackward (backspace). When deleting a newline with multiple cursors, the same issue exists - deleting a newline at cursor position merges two lines, causing all cursors below to shift up by 1 line. But the current code doesn't adjust other cursors after each deletion.

The fix pattern (from InsertNewline):
```
// After the deletion for this cursor:
for other_idx in 0..model.editor().cursors.len() {
    if other_idx != idx && model.editor().cursors[other_idx].line > deleted_line {
        model.editor_mut().cursors[other_idx].line -= 1;  // or += for insertions
        // Also adjust selections
    }
}
```

Test helpers available:
- test_model(text, line, col) in tests/common/mod.rs creates AppModel with single cursor
- model.editor_mut().add_cursor_at(line, col) adds additional cursors
- update(&mut model, Msg::...) dispatches messages

Here's **Bug #3** explained:

### The Problem

The `EditOperation` variants store **only a single cursor** for `Insert`, `Delete`, and `Replace`:

```rust
Insert {
    cursor_before: Cursor,  // ← single cursor!
    cursor_after: Cursor,   // ← single cursor!
}
```

But `Batch` correctly stores **all cursors**:

```rust
Batch {
    cursors_before: Vec<Cursor>,  // ← all cursors ✓
    cursors_after: Vec<Cursor>,   // ← all cursors ✓
}
```

When you do a **single-cursor operation** with multiple cursors active (e.g., undo an insert), the undo handler only restores the primary cursor:

```rust
// Line 1592 in apply_undo_operation
*model.editor_mut().primary_cursor_mut() = *cursor_before;  // Only restores 1 cursor!
```

### The Symptom

1. Create 3 cursors on lines 1, 2, 3
2. Type a character (all 3 cursors insert)
3. Press Undo
4. **Expected:** 3 cursors restored at original positions
5. **Actual:** Only 1 cursor remains (the primary)

### Why It Happens

Multi-cursor edits correctly use `EditOperation::Batch`, which preserves all cursors. But some single-cursor code paths (like when there's a selection) still use `Insert`/`Delete`/`Replace` even when multiple cursors exist.

### The Fix

Either:
1. Change `Insert`/`Delete`/`Replace` to store `Vec<Cursor>` instead of single `Cursor`
2. Or ensure all multi-cursor operations always use `Batch`

The test is currently `#[ignore]` to track this known issue.

1) TL;DR

- Yes: both issues you found are real bugs—the text edits from `Cut` and multi-cursor `Paste` are not recorded in the undo stack, so they can’t be undone.
- The correct fix is to follow the existing pattern: for single-cursor edits, push a single `EditOperation::{Insert,Delete,Replace}`; for multi-cursor edits, collect per-cursor `EditOperation`s and wrap them in an `EditOperation::Batch { operations, cursors_before, cursors_after }`.

2) Confirming the two reported bugs

### 1. `DocumentMsg::Cut` (lines 995–1075)

Current behavior:

- It computes `text_to_copy` from selections (multi or single).
- It writes to the clipboard.
- It then **removes text from the buffer**:
  - Multi-cursor: manual `buffer.remove(start_offset..end_offset)` for each selection.
  - Single-cursor: calls `delete_selection(model)` (which removes from `buffer`).
- It sets `is_modified = true` but **never calls `push_edit`** or otherwise adds an `EditOperation` to the undo stack.

Consequence:

- The buffer changes are not represented in `undo_stack`, so `Undo` cannot restore the cut text.
- This violates the invariant used everywhere else: “every user-visible buffer mutation must be represented by an `EditOperation` pushed via `push_edit`”.

So: yes, this is a real undo bug for both single- and multi-cursor cut.

---

### 2. `DocumentMsg::Paste` multi-cursor branch (lines 1093–1156)

Current behavior when `model.editor().has_multiple_cursors()`:

- Reads `text` from the clipboard.
- Case A: `lines.len() == cursor_count`
  - For each cursor (in reverse order), inserts `line_to_paste` via `buffer.insert(pos, line_to_paste)`.
  - Updates each cursor and selection.
- Case B: otherwise
  - For each cursor (in reverse order), inserts the entire `text` via `buffer.insert(pos, &text)`.
  - Updates cursor positions and adjusts other cursors if multiple lines added.

In *both* multi-cursor cases, there is:

- No `EditOperation` created per insertion, and
- No `EditOperation::Batch` pushed via `push_edit`.

- With selection: `Replace { position, deleted_text, inserted_text: text, cursor_before, cursor_after }`.
- Without selection: `Insert { position, text, cursor_before, cursor_after }`.

- Multi-cursor pastes change the buffer but don’t show up in `undo_stack`.
- Undo/redo for those pastes is broken.

3) Correct fix pattern (based on existing operations)

The codebase already has a clear pattern for undoable edits:

- **Single-cursor edits**:
  - Perform the buffer change.
  - Update cursor/selection.
  - Push one `EditOperation::{Insert, Delete, Replace}` via `document.push_edit`.
- **Multi-cursor edits**:
  - Capture `let cursors_before = editor.cursors.clone();`
  - `let indices = cursors_in_reverse_order(model);`
  - `let mut operations = Vec::new();`
  - For each cursor index in `indices`:
    - Compute offsets from cursor/selection.
    - Compute `deleted_text` or `inserted_text`.
    - Mutate `buffer`.
    - Mutate that cursor and its selection.
    - Push a per-cursor `EditOperation::{Insert, Delete, Replace}` into `operations`.
  - After the loop:
    - `let cursors_after = editor.cursors.clone();`
    - `document.push_edit(EditOperation::Batch { operations, cursors_before, cursors_after });`

Examples of this pattern:

- `InsertChar` multi-cursor: lines ~49–90.
- `InsertNewline` multi-cursor: lines ~143–197.
- `DeleteBackward` / `DeleteWordBackward` / `DeleteForward` / `DeleteLine` multi-cursor.
- `Duplicate`, `IndentLines`, `UnindentLines` multi-cursor.

Undo/redo mechanics depend entirely on these `EditOperation`s:

- `push_edit` puts them onto `undo_stack` and clears `redo_stack`.
- `Undo` calls `apply_undo_operation`.
- `Redo` calls `apply_redo_operation`.
- `Batch` operations:
  - Apply each inner operation buffer-only in reverse (undo) or forward (redo) order.
  - Then restore full `cursors_before` / `cursors_after`.

So the fix for `Cut` and multi-cursor `Paste` is: reuse those exact patterns.

That was a **bug I fixed**, not intentional behavior.

The original code had:

```rust
Key::Named(NamedKey::ArrowUp) if alt && option_double_tapped =>
```

The `#[cfg(debug_assertions)]` attribute was mistakenly applied to the `update()` call, which meant:
- **Debug builds**: Multi-cursor shortcuts worked
- **Release builds**: The match arm matched but returned `None` (no action)

I removed the debug attribute so it now works in all builds:

```rust
Key::Named(NamedKey::ArrowUp) if alt && option_double_tapped => {
    update(model, Msg::Editor(EditorMsg::AddCursorAbove))
}
```

This was likely left over from debugging the double-tap Option detection feature.
