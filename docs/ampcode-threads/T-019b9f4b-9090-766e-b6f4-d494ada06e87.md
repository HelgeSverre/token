- The native `render_preview_pane()` is still drawing markdown into the preview area, and the webview is being added on top as an overlay; there is no gating between them, so you see both. 3) Rationale and trade-offs

- For the preview, the simplest workable model is: **Renderer owns chrome, WebView owns content**. It avoids entangling the low-level renderer with webview details while eliminating overdraw and confusing dual rendering.

- For scrolling, matching `HoverRegion` to `FocusTarget` semantics (add `Dock`) is the most coherent fix. You already use hover to multiplex scroll; extending the enum is less invasive than trying to special-case coordinates inside the scroll handler.

4) Risks and guardrails

- **Preview alignment / DPI issues:** Your `to_wry_rect` currently ignores `scale_factor`:

  ```rust
  fn to_wry_rect(bounds: Rect, _scale_factor: f64) -> Rect {
      use wry::dpi::{LogicalPosition, LogicalSize};

      Rect {
          position: LogicalPosition::new(bounds.x as f64, bounds.y as f64).into(),
          size: LogicalSize::new(bounds.width as f64, bounds.height as f64).into(),
      }
  }
  ```

  If your editor coordinates are in **physical pixels** (they likely are, because `char_width` already includes scale_factor and softbuffer works in physical px), passing them as `LogicalPosition` will cause wry to apply DPI scaling a second time, which explains the screenshot’s misalignment.

  ```rust
  fn to_wry_rect(bounds: Rect, _scale_factor: f64) -> Rect {

      Rect {
          position: PhysicalPosition::new(bounds.x as i32, bounds.y as i32).into(),

### 2.4. Keep `to_wry_rect` in physical units

```rust

3) Rationale and trade-offs

- The header and padding offsets live purely in the view-layer (`Pane`), so the simplest and most robust fix is to reuse that same logic when computing webview bounds instead of guessing offsets.
- This avoids introducing any ad-hoc decoration or DPI hacks and keeps **one source of truth** for geometry.
- Using physical coordinates for both the softbuffer renderer and wry child webviews keeps the mental model simple: “one pixel in `Rect` == one device pixel in the window’s client area.”

Alternative (not recommended now): change the entire rendering/layout pipeline to use logical units and convert only at the boundary to softbuffer/wry. That’s a much larger refactor for little immediate benefit.

---

4) Risks and guardrails

- **DPI mismatch**: If `model.metrics.scale_factor` ever diverges from `window.scale_factor()`, your layout and webview bounds could drift. Guardrail: assert or log if they differ significantly.
- **Multiple compute_layout_scaled callers**: `compute_layout_scaled` is also called from hit-testing (`update_cursor_icon`, splitter drag). That’s fine, but be aware it mutates `preview.rect`. The authoritative rect used for webview bounds is the one set during `Renderer::render()` right before `sync_webviews()`.
- **Insets vs full content area**: If you choose the “header only” adjustment and not full `Pane` content insets, the HTML might start slightly closer to the header than native text would. If that visual discrepancy matters, switch to using `Pane::content_x()/content_y()` etc.

---

Revisit the design if:

- You add more complex preview chrome (toolbar, status strip) and want webview bounds to be dynamically driven by that.
- You start mixing logical and physical coordinates elsewhere (e.g., for input/mouse hit-testing) and see other DPI bugs; at that point, it may be worth centralizing all coordinates as logical and introducing explicit conversions at OS boundaries.

On macOS, WKWebView’s `setFrame:` uses:

- units: logical points, not physical pixels
- origin: **bottom-left** of the parent NSView’s coordinate system (unless the view is flipped)

- `bounds.x, bounds.y` are already in the same origin convention as wry expects (parent’s bottom-left).

fn to_wry_rect(bounds: token::model::editor_area::Rect, scale_factor: f64, window_height_px: f64) -> Rect {
    use wry::dpi::{LogicalPosition, LogicalSize};

    // Convert top-left based physical coords -> bottom-left based logical coords
    let logical_x = bounds.x as f64 / scale_factor;
    let logical_h = bounds.height as f64 / scale_factor;
    let logical_y = (window_height_px - (bounds.y as f64 + bounds.height as f64)) / scale_factor;

    Rect {
        position: LogicalPosition::new(logical_x, logical_y).into(),
        size: LogicalSize::new(
            bounds.width as f64 / scale_factor,
            logical_h,
        ).into(),
    }
}
```

- The code you showed for `update_bounds` and `to_wry_rect` is *structurally* correct: you’re calling `set_bounds` with a `Rect`, doing logical conversion, and ignoring the result (which you should now log).

- If you change your y-coordinate mapping, verify it across multiple window sizes and multiple monitors (scale factor changes).

On macOS, NSView (which WKWebView inherits from) uses bottom-left origin, while our editor uses top-left origin. The formula is:

```
bottom_y = window_height - (top_y + height)
