I implemented phases 1-5 of the keymapping system to migrate from hardcoded key handling in input.rs to a configurable YAML-based system.

What I built:
- New src/keymap/ module with types (Modifiers, KeyCode, Keystroke), Command enum (60+ variants), Keybinding, and Keymap structs
- YAML config parser that loads keybindings from keymap.yaml at project root
- Platform-aware "cmd" modifier that maps to Meta on macOS, Ctrl elsewhere
- Bridge integration in app.rs that tries keymap first for simple commands, falls back to input.rs for complex behaviors
- Chord support with KeyAction::{Execute, AwaitMore, NoMatch}
- 53 passing tests

Key architecture:
- winit KeyEvent -> keystroke_from_winit() -> Keymap::handle_keystroke() -> Command -> to_msgs() -> update loop
- Commands marked is_simple() go through keymap; complex ones (like EscapeSmartClear) fall back to input.rs
- keymap.yaml is embedded at compile time via include_str!, but also checked for runtime override

What still lives in input.rs (needs Phase 6 context system):
- Selection collapse on arrow keys (jump to selection start/end before moving)
- Tab insert vs indent based on selection state
- Escape cascade (multi-cursor -> selection -> nothing)
- PageUp/Down with selection (normalize selection first)
- Option double-tap for multi-cursor (temporal pattern, not a chord)

I added CommandId::to_keymap_command() mapping in commands.rs so the command palette can look up keybindings from the keymap.

The implementation plan is in docs/feature/KEYMAPPING_IMPLEMENTATION_PLAN.md. Remaining phases:
- Phase 6: Context system (KeyContext struct with has_selection, has_multiple_cursors, etc.)
- Phase 7: Migrate complex behaviors using context conditions
- Phase 8: Modal integration
- Phase 9-11: User config file loading, cleanup

---

3) Rationale and trade‑offs

- Reuse existing concepts:
  - `focused_group_id` + `active_tab_index` already encode “focused vs active”; no new model state is necessary.
  - `UiState.cursor_visible` remains a single global blink source used by both editors and modals.
- Minimal changes:
  - Only the render pipeline and hit‑testing logic change; no need to touch the core editor model or message types.
  - Cursor hiding is purely a view concern: the editor’s internal cursor positions remain unchanged; only the drawing is gated.
- Avoid complexity:
  - We do not introduce per‑group blink timers or per‑editor `cursor_visible` flags: that would complicate the model for little gain right now.
  - Tab‑bar hit‑testing is done in one place (the mouse handler), not by rearchitecting geometry or adding an explicit “widget tree”.

---

4) Risks and guardrails

- Layout must be up‑to‑date for hit‑testing:
  - `group.rect` is set in `EditorArea::compute_layout`, called from:
    - `Renderer::render` and
    - `App::update_cursor_icon`.
  - Cursor moves before clicks, so `CursorMoved → update_cursor_icon → compute_layout` ensures `group.rect` is fresh before most clicks.
  - Guardrail: if you ever change that flow, ensure you still call `compute_layout` before relying on `group.rect` for hit‑testing.
- pixel_to_cursor still assumes a single global editor:
  - It uses a global `TAB_BAR_HEIGHT` and the focused editor’s viewport, ignoring which group was clicked.
  - That’s orthogonal to the tab bar issue but is the next thing that will bite you as split support deepens.
- Behavior with modals:
  - We keep blinking cursors underneath the dimmed overlay; visually they’re de‑emphasized anyway.
  - If you want modals to “steal” cursor blink entirely (no blinking in editors while modal active), you could additionally gate with `!model.ui.has_modal()` in the editor cursor drawing condition.
- Empty tab‑bar clicks:
  - In the new code, clicking empty tab‑bar space consumes the event and does nothing. If you’d rather that also focus the group (without switching tabs), you can do that before the final `return None;`.

---

5) When to consider the advanced path

Consider a more complex design only if:

- You want truly per‑pane caret blink timing (e.g., last‑input‑wins, or independent timers when multiple panes are focused by different devices).
- You want accurate per‑group coordinate mapping for selection and scrolling:
  - e.g., clicks in lower panes should map using that group’s top y, not the global `TAB_BAR_HEIGHT`.
- You introduce other focusable UI widgets (sidebars, terminals, etc.) and need a unified focus tree, not just “modal vs editor group”.

---

6) Optional advanced path (outline only)

If you decide to go further:

1. **Introduce a unified focus enum** in `UiState`:

   ```rust
   pub enum FocusTarget {
       EditorGroup(GroupId),
       Modal(ModalId),
       // later: Sidebar, Terminal, etc.
   }

   pub struct UiState {
       ...
       pub focus: FocusTarget,
   }
   ```

   - Make `focused_group_id` a derived value from this enum.

2. **Per‑group cursor blink:**

   - Add `last_cursor_blink` and `cursor_visible` to each `EditorGroup` or `EditorState`.
   - `UiMsg::BlinkCursor` loops all editors and toggles only those in the currently focused group (or near enough).

3. **Per‑group hit‑testing end‑to‑end:**

   - Replace `geometry::pixel_to_cursor` uses with:
     - `group_at_point(x, y)` → find group + editor,
     - then `geometry::pixel_to_cursor_in_group` with that group’s rect, editor, and document.

This is a larger refactor (M–L) and not needed to solve your current issues, but it’s a clean direction if you keep investing in multi‑pane UI.
