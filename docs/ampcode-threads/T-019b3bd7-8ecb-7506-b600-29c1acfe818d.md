The search confirms that `softbuffer` is a CPU-based software renderer without hardware acceleration. The key issue with `ControlFlow::Poll` is that it causes the event loop to spin continuously, which can lead to excessive CPU usage and potentially blocking behavior.

Let me now focus on optimizing the event loop. The main issue is:
1. **`ControlFlow::Poll`** spins constantly, calling `about_to_wait` continuously
2. This causes constant redraw requests even when nothing changed
3. `present()` with VSync can block for up to 16.67ms

The fix is to use `ControlFlow::Wait` (or `ControlFlow::WaitUntil` for the cursor blink timer) and only redraw when needed:

If the `Frame`’s width/height are *device* pixels and the font is rendered at the same pixel scale, then there is no additional “scale factor” needed on top of this — the core issue is the layout using magic numbers that don’t scale with font size.

Where things would break:

- If the rest of the editor uses logical coordinates and then multiplies by a scale factor before drawing, but the overlay doesn’t, then the overlay will appear in the correct place but have all padding/margins “too small” on HiDPI. The fact that vertical spacing uses `line_height` (likely already scaled) but horizontal spacing uses constants (`80`, `180`, `380`) is a strong hint that only horizontal layout is effectively non‑HiDPI aware.

So:

- Tie *all* horizontal distances that are text-related to `line_height` or measured text width.
- It’s not necessary to introduce an explicit “scale factor” parameter here if `line_height` already incorporates DPI.

---

3) Rationale and trade-offs

- Root cause: hard-coded pixel assumptions for a layout that’s fundamentally driven by text width. On HiDPI, those assumptions are false because glyphs are physically wider.
- Fixing `chart_x` and overlay width to follow actual (or approximate) text width preserves the existing design and rendering pipeline while solving both overlap and clipping.
- This avoids adding any new dependencies or overlay system complexity; only a few constants and offsets change.

Trade-offs:

- Approximate calculations based on `line_height` won’t be pixel-perfect with every font, but will be robust across scale factors and “good enough” for a debug overlay.
- Adding a text measurement API to `TextPainter` is slightly more work but gives exact alignment; if that’s available, prefer it.

---

4) Risks and guardrails

- If you keep the chart width large and don’t increase overlay width enough, wide values (e.g., `123456 µs`) can still overflow; choose a “max expected” value and size the right column for that.
- If `line_height` happens to change (e.g., configurable font size), your derived layout will also change, which is desired, but verify that the overlay still fits into typical window sizes at very large fonts.
- Ensure that any new overlay width does not exceed `frame.width()` on small windows; `compute_bounds` will still place it on-screen, but content that extends further will draw off-screen (invisible but safe).

---

5) When to consider the advanced path

Revisit with a more sophisticated design if:

- You want multiple kinds of overlays with auto-sizing, not just perf stats.
- Users can choose arbitrary fonts/sizes, and you want overlays to always look tightly aligned with no wasted space.
- You anticipate needing localization/longer labels where hard-coded assumptions about max label width no longer hold.

---

6) Optional advanced path (brief)

- Extend `TextPainter` with methods like `fn text_width(&self, text: &str) -> usize`.
- Change overlays to:

  - Measure all pieces of text they plan to draw.
  - Compute a flexible grid: `label_col_width`, `sparkline_col_width`, `value_col_width`, plus margins.
  - Set `OverlayConfig::width` and `height` based on the sum of column widths and number of rows (instead of fixed 380×480).
  - Optionally add clipping so overlay content is guaranteed not to draw outside its bounds.

For your immediate problem, though, adjusting `chart_x` based on `line_height`/measured label width and increasing overlay width a bit is sufficient and low-risk.

**Fix Applied:**
1. Calculate a `scale` factor from `line_height` (which is already DPI-aware): `scale = line_height / 20.0`
2. Scale overlay dimensions: `420 × 500` at 1x scale
3. Scale padding, margins, bar widths, and chart dimensions using `scale`
4. Derive label width from approximate character width (`0.6 × line_height`)
5. Dynamically size chart to fit within overlay bounds

The overlay will now properly render on both standard and HiDPI displays, with labels, sparklines, and values fitting correctly without overlap.
