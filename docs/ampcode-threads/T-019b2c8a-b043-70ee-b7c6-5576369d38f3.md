### A. Treat `UiState.focus` as the single source of truth for keyboard focus

You’ve done the right first step by adding:

```rust

    Editor,
    Sidebar,
    Modal,
}

and:

```rust

    // ...
    pub focus: FocusTarget,
}
```

`open_modal` / `close_modal` and the sidebar mouse click logic all set `focus` – that’s good.

The main missing piece: **keyboard routing still lets editor logic run even when sidebar is focused**.

#### 1. Make sidebar focus gate the entire fallback handler

Right now in `handle_key`:

```rust
// Focus capture: route keys to sidebar when it has selection
if is_sidebar_focused(model) {
    if let Some(cmd) = handle_sidebar_key(model, &key, ctrl) {
        return Some(cmd);
    }
    // Fall through to other handlers if sidebar doesn't consume the key
}
```

After this block, you still run all the editor‑centric logic, including navigation and character insertion. That means:

- Arrow keys you don’t explicitly handle will still affect the editor.
- Typing `a`, `b`, etc. while sidebar is “focused” will still insert into the editor buffer.

That’s exactly the “focus handling” bug: focus doesn’t actually prevent the editor from receiving keys.

**Fix:** when the sidebar is focused, route keys exclusively to sidebar, and swallow everything it doesn’t handle.

```rust
use token::model::FocusTarget;

pub fn handle_key(/* ... */) -> Option<Cmd> {
    // 1) splitter drag cancel
    // 2) modal capture
    if model.ui.has_modal() {
        return handle_modal_key(model, key, ctrl, shift, alt, logo);
    }

    // 3) CSV capture
    if is_csv_editing(model) {
        return handle_csv_edit_key(model, key, ctrl, shift, alt, logo);
    }

    // 4) Sidebar capture – **do NOT fall through to editor logic**
    if matches!(model.ui.focus, FocusTarget::Sidebar) {
        // Sidebar only handles a subset of keys. For others we just consume the key
        // so it doesn't leak into the editor.
        return handle_sidebar_key(model, &key, ctrl).or(Some(Cmd::Redraw));
        // If you prefer keys to be pure no-op (no redraw), just return None instead.
    }

    // 5) Normal editor-focused handling
    match key {
        // existing multi-cursor, selection-collapse, typing logic...
    }
}
```

This makes the focus semantics clear:

- `focus == Sidebar`: only sidebar-specific navigation / actions run. Editor doesn’t see keys at all.
- `focus == Editor`: existing editor logic runs.
- `focus == Modal`: handled earlier via `has_modal()`; editor/ sidebar logic doesn’t run.

If you later want some “global” shortcuts to work regardless of focus (Cmd+P, Cmd+S), keep them in the keymap and give them conditions **not** tied to `EditorFocused` / `SidebarFocused`. `handle_key` is already only a fallback after keymap evaluation.

### C. Make scroll events target the correct component

Today the sidebar’s `scroll_offset` is part of `Workspace`, but there’s no `WorkspaceMsg::Scroll` and we haven’t seen any code that updates `scroll_offset`. That strongly suggests sidebar scroll is either:

- not hooked up at all, or
- mutated imperatively somewhere in `App` instead of going through the Elm-style update.

Either way, **scroll routing should be explicit and based on hover/geometry, not hidden state.**

#### 1. Add a sidebar scroll message

In your `WorkspaceMsg` enum:

```rust
pub enum WorkspaceMsg {
    // ...
    Scroll { lines: i32 },
}
```

In `update_workspace`:

```rust
WorkspaceMsg::Scroll { lines } => {
    if let Some(workspace) = &mut model.workspace {
        let total = workspace.visible_item_count();
        if total == 0 {
            return Some(Cmd::Redraw);
        }

        // How many rows can we show at once?
        let row_h = model.metrics.file_tree_row_height as f32;
        let window_h = model.window_size.1 as f32;
        let visible_rows = (window_h / row_h).max(1.0) as usize;

        let max_offset = total.saturating_sub(visible_rows);
        let cur = workspace.scroll_offset as i32;
        let new = (cur + lines).clamp(0, max_offset as i32);
        workspace.scroll_offset = new as usize;
    }
    Some(Cmd::Redraw)
}
```

You can refine `visible_rows` if the sidebar doesn’t use the full window height, but the pattern is the same.

#### 2. Route `MouseWheel` based on where the cursor is

In your `WindowEvent::MouseWheel` handler (not shown), do:

- If a modal is open and the wheel is over the modal, route to the modal (e.g. command palette list navigate) and ignore sidebar/editor.
- Otherwise, decide between sidebar vs editor based on geometry:

Pseudo-code:

```rust
WindowEvent::MouseWheel { delta, .. } => {
    let lines = match delta {
        MouseScrollDelta::LineDelta(_, y) => y as i32,
        MouseScrollDelta::PixelDelta(pos) => {
            // approximate pixel-based scrolling in lines
            (pos.y / self.model.line_height as f64).round() as i32
        }
    };

    if lines == 0 {
        return None;
    }

    let (x, _y) = match self.mouse_position {
        Some(p) => p,
        None => return None,
    };

    // If sidebar visible and mouse is over it: scroll sidebar
    if let Some(workspace) = &self.model.workspace {
        if workspace.sidebar_visible {
            let sidebar_width =
                workspace.sidebar_width(self.model.metrics.scale_factor) as f64;
            if x < sidebar_width {
                return update(
                    &mut self.model,
                    Msg::Workspace(WorkspaceMsg::Scroll { lines: -lines }),
                );
            }
        }
    }

    // Otherwise: scroll editor
    return update(
        &mut self.model,
        Msg::Editor(EditorMsg::Scroll(lines.signum())),
    );
}
```

Notes:

- This makes scroll **follow hover** (mouse location), which is what most editors do and generally feels right.
- Focus (`UiState.focus`) remains purely about keyboard input. You can keep scroll hover-based without entangling it with focus.
- If you prefer focus‑based scroll (scroll sidebar whenever it has focus, even if mouse is over editor), replace the hover check with `matches!(self.model.ui.focus, FocusTarget::Sidebar)`.

Effort: M (1–3h) including tuning.

### D. Introduce an explicit hover-region enum and use it for cursor icons & scroll

Right now, hit-testing is scattered:

- `is_in_modal` / `modal_bounds` in `geometry.rs`,
- `is_in_group_tab_bar` in `geometry.rs`,
- various ad hoc coordinate checks in `app.rs` (sidebar width, resize hit zone, etc.),
- probably some cursor icon changes using `CursorIcon`.

To make both hover states and scroll targeting reliable, introduce a tiny **hover region** type:

```rust
// In ui.rs or a small new module:
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum HoverRegion {
    None,
    Sidebar,
    SidebarResize,
    EditorText,          // or EditorText(GroupId) if needed
    EditorTabBar,
    StatusBar,
    Modal,
}
```

Add it to `UiState`:

```rust
pub struct UiState {
    // ..
    pub focus: FocusTarget,
    pub hover: HoverRegion, // new
}
```

Default:

```rust
hover: HoverRegion::None,
```

#### 1. Update hover on every `CursorMoved`

In `WindowEvent::CursorMoved`:

```rust
WindowEvent::CursorMoved { position, .. } => {
    let (x, y) = (position.x, position.y);
    self.mouse_position = Some((x, y));

    let mut hover = HoverRegion::None;

    // Modal takes precedence
    if self.model.ui.has_modal() {
        let (has_list, list_items) = match &self.model.ui.active_modal {
            Some(ModalState::CommandPalette(state)) => (true, filter_commands(&state.input).len()),
            _ => (false, 0),
        };
        if is_in_modal(
            x,
            y,
            self.model.window_size.0 as usize,
            self.model.window_size.1 as usize,
            self.model.line_height,
            has_list,
            list_items,
        ) {
            hover = HoverRegion::Modal;
        }
    }

    if hover == HoverRegion::None {
        // Sidebar & resize
        if let Some(workspace) = &self.model.workspace {
            if workspace.sidebar_visible {
                let sidebar_width =
                    workspace.sidebar_width(self.model.metrics.scale_factor) as f64;
                const HIT: f64 = 4.0;
                let resize_start = sidebar_width - HIT;
                let resize_end = sidebar_width + HIT;

                if x < resize_start {
                    hover = HoverRegion::Sidebar;
                } else if x >= resize_start && x <= resize_end {
                    hover = HoverRegion::SidebarResize;
                }
            }
        }

        // Editor regions (if not already modal/sidebar)
        if hover == HoverRegion::None {
            // Use group rects + is_in_group_tab_bar to distinguish tab bar vs text
            let tab_bar_h = self.model.metrics.tab_bar_height;
            let mut in_tab = false;
            for g in self.model.editor_area.groups.values() {
                if x >= g.rect.x as f64
                    && x < (g.rect.x + g.rect.width) as f64
                    && is_in_group_tab_bar(y, &g.rect, tab_bar_h)
                {
                    in_tab = true;
                    break;
                }
            }
            hover = if in_tab {
                HoverRegion::EditorTabBar
            } else if !geometry::is_in_status_bar(
                y,
                self.model.window_size.1,
                self.model.line_height,
            ) {
                HoverRegion::EditorText
            } else {
                HoverRegion::StatusBar
            }
        }
    }

    if self.model.ui.hover != hover {
        self.model.ui.hover = hover;
        // Set cursor icon based on hover:
        if let Some(window) = &self.window {
            let icon = match hover {
                HoverRegion::SidebarResize => CursorIcon::ColResize,
                HoverRegion::EditorText => CursorIcon::Text,
                _ => CursorIcon::Default,
            };
            window.set_cursor_icon(icon);
        }
    }

    None
}
```

This gives you:

- A single place that answers “what is under the mouse?”
- A clean driver for cursor icons.
- A value you can also reuse for scroll routing, if you prefer `hover` over direct geometry checks.

Effort: M–L (2–8h) depending on how many regions you want and how much existing code you refactor.

---

3) Rationale and trade-offs

- **Clear contracts**:
  - `UiState.focus` ⇒ who gets keyboard input.
  - `UiState.hover` / geometry ⇒ who reacts to the mouse (scroll, cursor icon, hovers).
- **Elm-style purity**: instead of mutating `scroll_offset` from `App`, `WorkspaceMsg::Scroll` keeps all state changes inside `update_workspace`.
- **Minimal changes**: Most fixes are small local edits (one early‑return in `handle_key`, an offset in sidebar hit-testing, plus an extra WorkspaceMsg/+Wheel handler).

Alternative design (more complex) would be a full focus stack / nested focus tree (editor vs per-modal sub-focus). That’s likely overkill for now.

---

4) Risks and guardrails

- If you over-constrain keymap conditions (e.g., all editor bindings require `EditorFocused`), you may unintentionally disable global shortcuts when sidebar is focused. Prefer global commands to **not** depend on `EditorFocused`/`SidebarFocused` unless truly region-specific.
- When you change scroll routing, verify trackpad behaviour on macOS (pixel deltas) vs wheel deltas on Linux/Windows; clamp scroll deltas to avoid huge jumps.
- Hover region logic should be kept in a single module (`geometry` + one place in `App`) to avoid desync between view and input; try not to reintroduce ad-hoc hit-tests elsewhere.

---

5) When to consider the advanced path

Revisit the design if:

- You add **multiple independently scrollable regions** (e.g., terminals, problems panel) and need a more generic “scroll target” concept.
- You implement complex modals with internal focus (text field vs list vs buttons) that need their own focus model beyond top-level `FocusTarget::Modal`.
- You start supporting keyboard‑driven region focus switching (e.g., Vim‑style “focus next pane") extensively; at that point a small focus manager abstraction may pay off.

---

6) Optional advanced path (outline)

If you reach that point, consider:

- Replace `FocusTarget` with a small **focus tree** (e.g., `enum FocusPath { Editor(EditorId), Sidebar, Modal(ModalId), StatusBar, ... }`).
- Track a **focus stack** to allow temporary focus capture (modal) with guaranteed restoration.
- Expose a generic `FocusedComponent` trait that can provide “keymap context” and handle scroll/keyboard, and make `App` just look up the current focus and forward events.

For now, the simple path above (tighten sidebar keyboard gating, add scroll messages, fix row indexing, and centralize hover) will make focus, scrolling, and hover behaviour predictable without overhauling your architecture.

Key points in this change:

- `scroll_offset` is passed into `render_node`.
- `visible_index` is the global flattened index; you:
  - Always increment it for each node.
  - Only draw when `idx >= scroll_offset`.
  - Only advance `y` for drawn rows.
- Children are still recursed into even if the parent row is above the viewport, so e.g. a deeply nested file can be visible while its folder header is scrolled off the top — same as VS Code.

This fixes:

1. **Rendering doesn't skip items before `scroll_offset`:**
   Items with `idx < scroll_offset` no longer affect `y` or draw anything.

2. **Y position doesn't account for scroll offset:**
   First drawn row (`idx == scroll_offset`) uses current `y` (initially `0`), so `scroll_offset` shifts which item appears at `y = 0`.

3. **Recursive `render_node` needs to know offset:**
   It now receives `scroll_offset` and uses `visible_index` to decide whether to draw or just count-and-recurse.

---

3) Rationale and trade-offs

- This mirrors the editor’s viewport behavior (`top_line`) and the command palette’s `.skip(scroll_offset)` pattern, but adapted to a tree.
- It reuses the existing recursive traversal and `visible_item_count()` logic; no new data structures or flattening APIs are required.
- Complexity stays low; runtime cost is still O(total visible items), which is acceptable for a file tree.

Alternatives considered (not chosen now):

- **Negative Y coordinates / drawing off-screen:**
  Would require signed coordinates and careful clipping; the rest of the renderer assumes `usize` and early-out by `y >= height`. It complicates logic for no real gain.

- **Pre-flattening the tree into a `Vec<(node, depth)>` each frame:**
  Would make the rendering loop look like the command palette’s, but adds allocations / extra passes. Not needed for correctness.

---

4) Risks and guardrails

- If `scroll_offset` becomes inconsistent with `visible_item_count()` (e.g., after a big expand/collapse), some indices might be out of bounds. You already clamp `scroll_offset` in `WorkspaceMsg::Scroll`, so that’s mitigated.
- If you later change `file_tree_row_height` or introduce a header area in the sidebar, ensure the scroll calculations (`visible_rows`, `clicked_visual_row`) and rendering all agree on what “row 0” is.

---

5) When to consider the advanced path

Consider a more complex design (e.g., pre-flattened tree with stable indices and explicit viewport structs) if:

- You add virtualized rendering for very large trees (tens of thousands of nodes), and the O(N) recursive pass becomes a measurable bottleneck.
- You need multiple independent views of the same tree (e.g., split sidebar panes with different scroll positions), which would benefit from a reusable, flattened representation.

---
